# Аппаратные блоки Sparrow, используемые прошивкой

Справочник по аппаратным ресурсам wil6210 (Sparrow), с которыми работают fw и ucode:
карта памяти, регистры RGF, блок TSF и таймеров MAC, прерывания, регистры ядра ARC.
Метки: **[драйвер]** — имя/адрес из mainline-драйвера `wil6210.h`; **[код]** — по
листингу прошивки; **[железо]** — проверено на стенде. Адреса регистров общие для
**[обе]** версий; адреса функций и переменных ОЗУ — **[4.1]**, если не указано иное.
Полная карта периферийных регистров 6.2 — `6.2/ref/REGS-62.md` (`make regs`).

## Карта памяти **[драйвер]**

Из `sparrow_fw_mapping`:

| диапазон (адреса прошивки) | хост-окно | имя | размер | доступ хосту |
|---|---|---|---|---|
| 0x000000–0x040000 | 0x8c0000 | `fw_code` | 256 К | да |
| 0x800000–0x808000 | 0x900000 | `fw_data` | 32 К | да |
| 0x840000–0x860000 | 0x908000 | `fw_peri` | 128 К | да |
| **0x880000–0x88a000** | 0x880000 | **`rgf`** (регистры) | 40 К | **да** |
| 0x88a000–0x88b000 | — | `AGC_tbl` | 4 К | да |
| 0x88b000–0x88c000 | — | `rgf_ext` | 4 К | да |
| 0x88c000–0x88c200 | — | `mac_rgf_ext` | 512 Б | да |
| 0x8c0000–0x949000 | — | `upper` | 548 К | да |

Доступные регионы читаются с хоста через debugfs `mem_addr`/`memread`.

**Адресация от базы 0x887000 [код].** В ucode регистры RGF часто адресуются от
**`0x887000` отрицательными смещениями** (`mov r2,0x887000; st.as rX,[r2,-0x2d0]`).
Поиск по абсолютному адресу регистра такие обращения не находит — искать надо
базу и смещение.

## Блок TSF и таймеров MAC (0x886d18…0x886ec0)

| адрес | имя (4.1) | имя в `REGS-62.md` | назначение |
|---|---|---|---|
| **0x886d18** | таймер пробуждения (pre-TBTT) | `mac_bi_reload_us` | перезагрузка таймера BI, мкс: период − 7 − 1; при BI 50/100/200 → 0xc7f8/0x18ff8/0x31ff8 = BI·1024 − 8 **[железо]**; 0 при невключённом MAC |
| **0x886d1c** | упреждение (lead) | `mac_bi_reload_clk` | дробная часть той же перезагрузки в тактах 165 МГц: `0xa5 − early` = 165 − 80 = 85 (0x55) при любом BI и канале **[железо]** |
| 0x886d30 | `TSF_TARGET_LO` | `mac_tsf_event_lo` | целевой TSF компаратора, младшее слово |
| 0x886d34 | `TSF_TARGET_HI` | `mac_tsf_event_hi` | целевой TSF компаратора, старшее слово |
| 0x886d38 | `TSF_EVENT_CTL` | `mac_tsf_event_ctrl` | **0xc0050 = взведён** (бит 6), **0xc0010 = снят**; 0 при входе в простой |
| 0x886d64 | период BI | `mac_beacon_interval` | [15:0] интервал маяка в TU (период_мкс >> 10); одиночная запись на лету останавливает маячный цикл; писатели по версиям — [BEACONING.md §7](BEACONING.md#7-период-bi-и-tbtt) **[железо]** |
| 0x886dc0/0x886dc4 | — | `mac_cmd0d_time_lo` | 64-битная защёлка аргумента MAC-команды 0x0d (первый TBTT при запуске BI) |
| 0x886dd4 | причины L1-прерывания | `fw2uc_ICM` | маскированная причина (ICR & ~IMV); биты 0/1/2 → разные L1-события |
| 0x886e84 | маска/лимит NAV (`nav_db.c`) | `mac_nav_hw_value` | младшие 16 бит читаются при обновлении NAV по Duration (`rx_nav__set_from_duration`, предел из 0x80146c+0x18); на стенде в простое 0x13, под iperf до 1982 (≈ TXOP 2000 мкс − 18), бит 31 — флаг **[железо]**; аппаратный NAV по Duration кадров партнёра **[гипотеза]** |
| 0x886eb4 | `TSF_STATUS` | `mac_timing_status` | бит 31 = значения времени MAC действительны; читатели TSF ждут его перед чтением |
| 0x886eb8 | `TSF_CUR_LO` | `TIMING_INDIRECT_REG_5` | текущий TSF, младшее слово, мкс |
| 0x886ebc | `TSF_CUR_HI` | `mac_tsf_hi` | текущий TSF, старшее слово |
| 0x886ec0 | — | `mac_usec_to_tbtt` | обратный отсчёт до следующего TBTT, мкс, 26 бит; максимум ≈ BI·1024 при BI 50/100/200; при невключённом MAC — 0x3ffffff **[железо]** |
| 0x886fc4 | — | — | TSF текущего TBTT, шаг BI·1024, сетка от нуля TSF; на следующий TBTT переводится за ~7–8 мс до него **[железо]** |

### Компаратор TSF **[код]**

Аппаратный компаратор: ucode кладёт момент срабатывания в `TSF_TARGET_*` и включает
`TSF_EVENT_CTL`; по достижении TSF железо генерирует событие.

Обёртки в ucode:

| адрес | имя | роль |
|---|---|---|
| 0x930c28 | `set_tsf_event` | взвод: запись в журнал, слово 0x02000040 в кольцо команд MAC, заряд компаратора 64-битным TSF |
| 0x925120 | `disable_tsf_event` | снятие |

Во всей прошивке 4.1 (fw+ucode) эти регистры трогают только две указанные функции
(косвенные вызовы через указатели формально не исключены). `set_tsf_event`
вызывается единственным местом — развёрткой маяка
`bti_worker__bti_transmitter_beacon_sweep_flow` (0x923de0, рандомизатор отсрочки);
`disable_tsf_event` — обработчиком команды конфига биконинга `ucode_cmd__bi_config`
(0x932f8c). У компаратора один владелец, и `TSF_TARGET − TSF_CUR` отражает задержку,
вычисленную рандомизатором; на этом основан `SparRAW-tools/host/wil_tsf_probe.py`.
Передача маяка от срабатывания компаратора не зависит, цель рандомизатора может лежать в
прошлом — [BEACONING.md §9](BEACONING.md#9-состояние-на-железе). В 6.2 те же регистры пишут также
`ucode_cmd_0x01_handler` и `mac_mode__enter_idle_seq` (`6.2/ref/REGS-62.md`).

### Программирование таймера BI **[код]**

`mac__program_deadline_slack` (0x930494):

```c
void mac__program_deadline_slack(int value, int offset, int early) {
    0x886d1c = 0;
    if (early == 0) 0x886d18 = (offset == 0) ? 0 : (value - offset);
    else          { 0x886d18 = (value - offset) - 1;
                    0x886d1c = 0xa5 - early; }      /* 0xa5 = 165 тактов = 1 мкс */
}
```

Вызовы (всего 3):

| место | аргументы | смысл |
|---|---|---|
| `shallow_sleep_rfc_step` (0x9219c8) | `(BI, 0x19, 0x50)` | перезагрузка BI − 25 − 1 мкс, 85 тактов |
| `power_manager__decide_shallow_sleep` (0x92ad98) | `(BI, 7, 0x50)` | BI − 7 − 1 мкс, 85 тактов (штатное значение на стенде) |
| `txrx_api_cmd_step` (0x931ce8) | константы 4, 7, 8, 10, 17, 19 рядом | ещё один профиль |

### Параметры BI, контур событий и ворота передачи маяка

Путь параметров BI от WMI до регистров (`bcn_tx_init_bi_cfg` → LMAC 0x0B →
`ucode_cmd__bi_config` → `bi_cfg__apply` → 0x801434 → 0x886d18/1c), контур событий биконинга
(`l1_task__entry` → `bi_manager__kind_switch` → `bi__decide_beacon_kind` → развёртка),
ворота BTI (`uc_bi_counter_in_window`, `uc_read_bi_sync` по `BI_COUNTER`) и NAV-отсрочка
маяка — [BEACONING.md](BEACONING.md) (§2–§5, адреса обеих версий). Раскладка 32-байтового
конфига `0x801438` (поле Beacon Interval Control 802.11ad) —
[4.1/docs/BEACON-CONFIG.md](../4.1/docs/BEACON-CONFIG.md).

## Публикация адресов логов **[драйвер]+[код]**

| адрес | имя [драйвер] | назначение |
|---|---|---|
| 0x880004 | `RGF_USER_USAGE_1` | адрес кольца лога **FW** |
| 0x880008 | `RGF_USER_USAGE_2` | адрес кольца лога **ucode** |
| 0x880018 | `RGF_USER_USAGE_6` | флаг «прошивка загружена хостом» (бит 0) |
| 0x880020 | `RGF_USER_USAGE_8` | флаги хоста |

Прошивка публикует здесь адрес своего лог-буфера; драйвер обнуляет USAGE_1 и
USAGE_2 перед стартом (`wil_pre_fw_config` → `wil_clear_fw_log_addr`), так что
ненулевое значение после загрузки означает, что лог опубликован. Полные раскладки
USAGE_1…USAGE_8 для 6.2 — `6.2/ref/REGS-62.md`.

### Кольцо лога ucode в ОЗУ **[код]** **[4.1]**

| адрес | назначение |
|---|---|
| 0x8020b0 | кольцо записей (256 × 4 Б) |
| 0x80209c | индекс записи |
| 0x8020a0…0x8020af | 16 байт уровней журнала по модулям; проверяется бит 2 |

`uc_log__init` (0x937f68) безусловно пишет 0x07 во все 16 байт уровней, поэтому
журнал ucode открыт всегда. Формат слова: `(hdr<<16) | offset_строки`; биты [3:2]
старшего байта hdr — число аргументов; аргументы кладутся в кольцо перед
словом-заголовком.

## Тактирование и сброс **[драйвер]**

## DMA и модерация прерываний (ITR) **[драйвер]**

`0x881c5c`/`60`/`64` ITR_CNT_TRSH/DATA/CRL; TX-блок `0x881d34..0x881d40`,
TX-idle `0x881d60..68`; RX-блок `0x881d44..0x881d50`, RX-idle `0x881d54..5c`;
`0x881d6c` DMA_MISC_CTL; `0x881cd4` DMA_OFUL_NID_0; `0x88265c` HP_CTRL.
Эти регистры драйвер экспортирует в debugfs на запись (`doff_io32`) — единственные,
доступные на запись штатно.

## OTP / XPM **[драйвер]**

`0x880ce0` OTP_HW_RD_MACHINE_1; `0x880cec..0x880d10` XPM_IFC_RD_TIME1..10;
`0x880d64` XPM_RD_DOUT_SAMPLE_TIME. В ucode есть соответствующие функции

## Таблицы AGC **[код]**

Грузятся из образа прошивки отдельными data-записями в регион `AGC_tbl`:
`0x88a004` (512 Б), `0x88a208` (1 КБ), `0x88a608` (2 КБ). В дереве —
`src/data/agc_tbl_004.S`, `agc_tbl_208.S`, `agc_tbl_608.S`.

## Регистры ядра ARC, используемые ucode **[код]**

| ресурс | назначение |
|---|---|
| **r47** | аппаратный ГСЧ — источник случайности для отсрочки маяка |
| `mlo` / `mhi` | результат 64-битного умножения (`mulu64`); `mov r0,mhi` — старшие 32 бита, т. е. `>>32` |
| **r25** | указатель на аппаратное кольцо команд MAC: `st.ab rX,[r25,0x4]` + `bclr r25,r25,0xa` (заворот на 1024 Б = 256 записей) |
| **r40** | результат чтения регистра MAC через кольцо |
| `gp` | база глобалов; переменные адресуются как `[gp, ±off]` (ucode 0x800528) |
| `_LP_START` / `_LP_END` | аппаратные регистры цикла ARC (zero-overhead loop) |

### Доступ ucode к MAC через кольцо

```asm
mov  r1, <gp-0x44> & 0xffff0fff | 0x4000   ; выбрать регистр
st   r1, [gp,-0x44]                         ; сохранить селектор
*r25 = r1 | 0x1d004000                      ; запрос в кольцо MAC
...                                          ; результат появляется в r40
uVar = in_r40 & 0x3ffffff
```

| ресурс | роль |
|---|---|
| r25 | кольцо запросов к MAC |
| r40 | регистр результата |
| `gp-0x44` | теневая копия селектора |
| `0x1d00xxxx` | операция «чтение регистра MAC» |
| `0x52000000`, `0x49000040`, `0x32000000` | другие команды MAC (TX-поток) |

Многие регистры MAC не видны как обращения к памяти: ucode общается с MAC через
кольцо команд. Селекторы и регистры — [MAC-REGISTERS.md](MAC-REGISTERS.md); коды
команд — [MAC-COMMANDS.md](MAC-COMMANDS.md).

## Доступ с хоста

* Чтение любого регистра доступного региона — debugfs `mem_addr`/`memread`
  (`SparRAW-docs/research/OBSERVABILITY.md`).
* Запись штатно — только в ICR/DMA/ITR-регистры (`doff_io32`); для прочих нужен
  патч драйвера (запись в таблицу debugfs).
* Запись в регистры, которыми управляет ucode (компаратор TSF, кольца), — борьба с
  прошивкой за ресурс; для диагностики достаточно чтения.

## Счётчики приёма PHY **[код + железо]**

`phy_stats__dump` 0x8e8ac0 **[6.2]** снимает 14 регистров через `phy__read_rx_counters`
(структура +0…+0x34) и печатает часть из них:

| регистр SC / CP | поле структуры | смысл |
|---|---|---|
| 0x883964 / 0x8839a0 | +0x00 / +0x1c | INA_SYNC (обнаружение преамбулы) |
| 0x883968 / 0x8839a4 | +0x04 / +0x20 | SFD_SYNC |
| 0x88396c / 0x8839a8 | +0x0c / +0x28 | HEADER_CRC_OK |
| 0x883970 / 0x8839ac | +0x14 / +0x30 | BER_LAST_ZERO (живьём 0) |
| 0x883974 / 0x8839b0 | +0x08 / +0x24 | SFD_TIMEOUT |
| **0x883978 / 0x8839b4** | +0x10 / +0x2c | **HEADER_CRC_ERROR SC / CP** |
| **0x88397c / 0x8839b8** | +0x18 / +0x34 | **BER_LAST_NON_ZERO SC / CP** |

Имена всех пар подтверждены раскладкой события UT 0x422
`hwd_phy_rx_get_statistics` (поля +0x00..+0x34, wmiUT.xml пака 11ad; привязка
через таблицу UT 6.2) **[пак]** и согласуются с PHY_LOG 4.1. PHY_ERROR_DP/CP в
LINK_STATS — это HEADER_CRC_ERROR SC/CP (0x883978/0x8839b4). Полная карта —
[REGS-62](../6.2/ref/REGS-62.md). Регистры свободно бегущие; сброс —
`hwd_phy__rx_statistics_lock` / `hwd_phy__rx_statistics_clear` при ненулевом
`[0x800524+0x34]`. С хоста читаются через `mem_addr`/`mem_val` (скрипт
`SparRAW-tools/bench/62/phyc.sh`).

**Счётчики сбрасывает ucode:** `phy_stats__accumulate_to_shared` 0x92e544
вычитывает их в общий блок `0x8576ac…0x857720` (суммы, 64-битные — парами) и
обнуляет регистры (`hwd_phy__rx_statistics_lock` /
`phy_stats__clear_counters_883960`), поэтому значение между снимками падает.

### Метод

Два снимка счётчиков ничего не значат: мерить только суммой положительных
приростов с опросом раз в секунду (`SparRAW-tools/bench/62/phyrate.sh`). У 4.1
счётчики почти нулевые — её PHY_MON вычитывает и сбрасывает их каждый BI.

**Замер (сумма за 20 с, CP: обнаружений / SFD / годных заголовков / ошибок) [железо]:**

| пара | где мерили | покой | под аплинк-пингом |
|---|---|---|---|
| AP 4.1 + STA 6.2 | STA | 9 071 / 8 950 / 8 458 / 719 | 9 878 / 9 822 / 9 886 / 174 |
| AP 6.2 + STA 6.2 | STA | 12 260 / 10 910 / 10 823 / 90 | 23 665 / 20 372 / 19 984 / 396 |

Станция 6.2 слышит CP-кадры AP 6.2 не хуже, а чаще, чем AP 4.1 (под пингом —
вдвое: это ответные развёртки).

## Замечания

* Бит 31 `BI_COUNTER` (ворота B) — `bi_sync`, а не CCA/NAV и не «маяк принят»;
  программной ветки «услышал чужой маяк — молчу» в воротах нет, отсрочка идёт через NAV.
* Окна BI (BTI/AW/DTI) ведут GP-таймеры MAC (события по битам r54), а не компаратор
  TSF; компаратор служит только отсрочке маяка.

## Не установлено

* Значение 0x19 во втором профиле `mac__program_deadline_slack` и роль профиля
  `txrx_api_cmd_step`.
* Кто пишет `0x801434` (BI): записи в ucode не найдено; вероятно, приходит тем же
  конфигом или ставится fw другим путём.
* Точный смысл `0x886e84` (текущий NAV или предел).
