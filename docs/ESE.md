# Расписание ESE (802.11ad TDMA)

Штатное расписание 802.11ad: поле Allocation элемента Extended Schedule (ESE) в маяке
PCP задаёт слоты DTI по AID источника и назначения. Команда хоста —
`WMI_SCHEDULING_SCHEME_CMDID` 0xa01 (обработчики обеих версий — [WMI.md](WMI.md)),
событие-ответ 0x1a01. Подсистема есть в 4.1.0.1000 и 6.2.0.1000 **[обе]**; слой
фиксированного расписания (гранты, RD) — только в 6.2,
[6.2/docs/FIXED-SCHED.md](../6.2/docs/FIXED-SCHED.md). Приём ESE из маяка —
шаг 5 обработчика DMG-маяка ([MLME.md §5](MLME.md#5-приём-management-кадра-discovery-и-dmg-маяка-код)).

Метки: **[код]** — по листингу. Запись адреса: `имя` 0x… — адрес 6.2; «/ 4.1 0x…» —
адрес той же функции в 4.1 (по совпадению тела, таблице
[NAMES-FROM-62](../4.1/docs/NAMES-FROM-62.md) или имени). Функции без пометки 4.1 —
соответствие не установлено. Адреса данных (0x805250, 0x803c00) — 6.2.

## 1. Устройство в 6.2 **[код]**

Поле Allocation ESE —
15 Б (контроль 2, BF-контроль 2, AID источника +4, AID назначения +5, начало
+6..+9, длительность +0xa..+0xb, …).

* С хоста: `wmi_ese_cfg` → `schedule_scheme_builder__build_allocations` 0x8c52cc
  («Number of slots in cmd»): очистка схемы
  (`schedule_scheme_builder__build_allocations_8c68a0` 0x8c68a0 — «Clearing
  scheme», снимает app-IE), для каждого слота — поле ESE для маяка по шаблону
  0x805250 (`sched__build_alloc_entry` 0x8c2ca4) и запись в свою таблицу
  (`schedule__build_allocation_entry` 0x8c2cf8), затем `add_bcon` —
  переиздание маяка с новым ESE. `sched__slot_start_offset` 0x8ccc48 —
  проверка непересечения («IDO cur_slot_start_offset / m_last_slot_end_offset»).
* С маяка PCP (STA): `schedule_scheme_builder__build_allocations_from_beacon`
  0x8c5248 — число полей = длина/15; `sched__alloc_changed` 0x8da3f4 решает,
  изменилось ли ESE (число и первое поле; при флаге в 0x803c00+0x10 — режим R2 OOB,
  [ROLELESS-LINK §1.7](ROLELESS-LINK.md#17-режим-oob-в-62-код) — по
  счётчику +0x18); при изменении таблица чистится
  (`sched_builder__reset_alloc_list` 0x8e2948), и каждое поле, где узел —
  источник или назначение (`cid_pair__matches` 0x8da62c: AID = свой или 0xff),
  превращается в запись слота **`ese__alloc_to_slot` 0x8c7d4c** (поле ESE →
  запись слота): 12 Б {ID и тип аллокации, бит «узел — источник», CID пира,
  AID src/dst, начало − база, длительность}. CID пира — `ese__peer_cid_by_aid`
  0x8cc9c8 (если источник — сам узел, пир = назначение, иначе источник; поиск
  CID по AID), вставка — `ese__slot_table_add` 0x8e1d38: **не более 3 записей**
  по 12 Б, иначе фатал 0x11bb. Печать «Got %d slots for me from total of %d
  slots».
* Фиксация: `schedule_scheme__sum_two` 0x8e0d48 — база следующего BI =
  `mac__get_bi_start_tsf` 0x8e457c (0x886fc4) + `mac__get_beacon_interval_us`
  0x8e456c (младшие 16 бит 0x886d64 — период маяка — ×1024, т. е. TU → мкс), и
  два прохода `lmac_if__evt_walk` (передача в ucode).
* Геттеры полей расписания: `mac_tx_cnt__get_ok`, `mac_tx_cnt__get_fail`,
  `mac_tx_cnt__delta_88_net_of_20` 0x8dd768 (зовут `sm_pring__bind_vring`,
  `link_stats__calc_goodput`); `seq__next_nibble` 0x8cb818;
  `sm_pring__all_wb_done_evt` 0x8c3180 / 4.1 0x8c29f4 → `tx_queue__config_by_mode`;
  `obj__has_pending_1c_10`.
* IE для кадров управления: `ie__push_edca` 0x8e1da8 / 4.1 0x8ef7b8 («Pushed EDCA IE»),
  `ie__push_eid151_len10` 0x8e1fbc / 4.1 0x8ef864; `lmac_if__send_sta_cfg_05_c` 0x8dc3c4 и
  `conn__alloc_and_fill` 0x8dc43c — команда LMAC 0x05 (конфигурация станции)
  через кольцо команд; 0x886d80 — лишь база смещений, звонок ucode — ICS
  0x886dd8 ([REGS-62](../6.2/ref/REGS-62.md)).

## Замечания

* В 6.2 таблица слотов узла вмещает не более 3 записей (фатал 0x11bb). В 6.4
  (`6.4/src/c/fw/ese__slot_table_add.cpp`) лишняя аллокация отбрасывается с
  предупреждением `ESE: slot table full`, узел не падает.

* 6.4: точка с расписанием ставит CBAP Only = 0, станция такой маяк принимает (патч 0011) —
  на стенде (2026-09-29) расписание от хоста (WMI 0xa01 одной записью в `wmi_send`)
  станция разбирает («[PRS] ESE EI ID=144, EI_LEN=45»), линк держится **[железо]**.
  Маска включённых qset (`[gp-0x7c]`, host 0x9404ac) закрывает передачу сразу, но обратная
  запись 0x70 очередь соседа не вернула — этот рычаг не годится **[железо]**.

## 3. Как 6.2 исполняет расписание **[код, железо]**

* **Аппаратный массив SP.** `lmac_if__evt_walk` закладывает записи {начало, конец,
  управляющее слово}; при бите 7 записи = 0 («не источник») в слове стоят
  `start_mask_ind`/`end_mask_ind` (биты 28/26). На стенде это **аппаратная маска
  передачи на время SP**: запись 0x14000040 (нулевая, «не источник») останавливает TX.
  Каждая 4-я запись несёт бит 6 — ucode по её началу шлёт событие 0x29, и прошивка
  закладывает следующие 4.
* **Запрет колец хоста по окнам.** На начало и конец каждого окна `dti_worker` шлёт
  событие PS тип 6 (`SCHEDULED_DTI_ALLOC`, +2 вектор CID пира, +4 маска). Прошивка
  (`ps_assoc_mgr__shallow_sleep_enter`, ветка 2) разрешает кольца передачи только CID
  вектора и запрещает остальные: `vring_schd` (объект 0x804dbc, vtable 0x8008e8:
  +0x1c `vring_schd__prohibit_cids` 0x8e1228, +0x20 разрешение 0x8c371c), маска
  запрета 0x804e60. На стенде без расписания маска 0, в окне 0xfffffefe (CID 0
  разрешён), вне окна 0xfffffeff. Конец окна идёт с пустым вектором — «запретить всех».
  То есть кольца хоста 6.2 вне окон закрывает; но в SP, где узел только назначение, пир
  окна разрешён — узел может инициировать, что 10.39.6.2 запрещает.
* **Дефект снятия расписания (6.2).** После снятия (`num_of_allocations` = 0) ucode
  продолжал просить записи, `lmac_if__evt_walk` закладывал нулевые (с маской TX), а
  последний конец окна оставлял запрет всех CID: передача вставала у точки и у
  станции навсегда **[железо, и на образе без правок 6.4]**.

## 4. 6.4 apsta: станция соблюдает расписание (802.11-2020 10.39.4, 10.39.5, 10.39.6.2)

* Патч 0018 (`6.4/patches`), `6.4/src/c/fw/new/ese_rx.cpp`: в таблицу идут SP, где станция источник или
  назначение, и CBAP с Source AID = свой или 255 либо Destination AID = свой; прочие
  типы, чужие окна и SP с адресом 255 (в том числе «барьер» 255→255) не берутся. Бит 7
  записи — «инициировать можно» (свой SP-источник, разрешённый CBAP). ESE сравнивается
  целиком (прежде — только ID и адреса первого поля). По каждому маяку своей точки
  ставится флаг «DTI расписан» (ESE есть, CBAP Only = 0, не вендорское фиксированное
  расписание) в общей ячейке ucode 0x803a60 (`ESE_DTI_OFS`, fw_uc_shared.h).
* Патч 0019, `6.4/src/c/uc/new/ese_dti.cpp`: при флаге передача станции ставится на паузу
  в начале DTI (`bi__dti_step`) и снимается только на окна с битом 7; в конце окна
  снова пауза. Рычаг — `bf__pause_sta_tx`/`bf__resume_sta_tx` со своей причиной 8:
  маска причин на CID (0x802a90), очереди возвращаются только после снятия последней
  причины, поэтому гонки с запретом BF (причина 3) нет. Мгновенные ответы идут мимо
  очередей — роль назначения сохраняется.
* Патч 0020 и вставка «closing slot»: из пустой таблицы записи не закладываются, а
  конец окна при пустой таблице несёт вектор «все CID» — запрет снимается.
* Стенд (2026-09-29): SP точка→станция на [2, 98) мс — станция молчит (ping и iperf
  вверх стоят, qset закрыт, причина 8 взведена); CBAP 255 на [2, 30) и [64, 100) мс и
  чужой SP 5→6 — 765/761 Мбит/с против 895/990 без расписания, ping до 23–28 мс
  (ожидание окна); после снятия — 954 Мбит/с, разрывов нет; PS без графика не задет.
* Сторона точки: 6.4 ставит CBAP Only = 0 при ESE (Ф5, 10.39.6.3); собственные SP
  чужим парам точка пока не соблюдает (её таблица их не хранит).

## Не установлено

* Раскладка таблицы слотов 4.1 и её предел; путь `parse_ese` → ucode в 4.1.
* Почему скорость вверх под расписанием (765 Мбит/с) выше доли открытых окон (~66 %):
  вероятно, уже выбранные в TXOP кадры дотекают после паузы; граница TXOP (R40) до
  конца окна не проверена.
* Блоки аллокации (Number of Blocks) и таблица больше 3 записей (Ф3) не сделаны.
