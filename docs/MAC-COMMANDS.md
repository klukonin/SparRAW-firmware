# Кольцо команд MAC (uCode CORE WRITE)

Справочник по командам, которые микрокод Sparrow посылает аппаратному MAC одним 32-битным словом:
порт записи, формат слова, журнал в памяти, способ снятия на железе, полное пространство кодов
с назначением и уровнем доказанности, типовые последовательности и связь с регистрами MAC.
Пространство кодов одинаково в 4.1.0.1000 и 6.2.0.1000 **[обе]**; измерения на железе сделаны на 4.1.

Метки доказанности: **[железо]** — проверено на стенде, **[код]** — по листингу, **[пак]** — по вендорским
исходникам пака 11ad, **[гипотеза]** — не проверено.

## 1. Интерфейс core write

**[пак]** Вендорское имя механизма — **uCode CORE WRITE**, порт — локальная запись в блок SXD:

    MAC_RGF.MAC_SXD.LOCAL_REGISTER_IF.LOCAL_WR_REG.sxd_local_wr_data   = 0x886dc8 (биты 0..31)

Источник — исходники `host_manager_11ad/PmcCommandHandler/` пака 11ad: `PmcSetConfigHandlerSequences.cpp`
(комментарий-таблица) и `PmcRegistersAccessor.cpp` (карта адресов).

* Блок SXD занимает 0x886d00..0x886dff. Микрокод 6.2 обращается к нему явно: 0x886d80 — 34 раза,
  0x886d00 — 28 раз, и ещё девять адресов **[код]**.
* Изнутри ядра ARC команда уходит не по AHB, а записью в регистр ядра `r32` (`mov r32,rX`) — отсюда
  «core write». Запись в 0x886dc8 с хоста команду **не исполняет** (§4) **[железо]**.
* Парный путь чтения — регистровый файл `MSXD_LR_RGF` (локальное чтение), запрос селектора идёт
  командой 0x1d (§7.3); см. [MAC-REGISTERS](MAC-REGISTERS.md) и `6.2/ref/MSXD-LR-RGF.txt`.
* Кольцевые коды — отдельный протокол от LMAC-команд (почтовый ящик с 16-байтовой шапкой,
  [LMAC-PROTOCOL](LMAC-PROTOCOL.md)). Совпадения номеров случайны: «кольцевой 0x1e» и «LMAC 0x1e»
  (`CMD_SELECTIVE_NEIGHBOR_CFG`) — разные вещи.

### 1.1. Формат слова

| биты | поле |
|---|---|
| 31 | в Sparrow: продублировать слово событием PMC (§1.3) |
| 30..24 | код команды |
| 23..0 | параметр (24 бита, поля упакованы плотно, без выравнивания; границы 8 и 16 встречаются чаще прочих) |

**[пак]** Раскладка «старший байт = код» подтверждена таблицей User Defined Command Register:
`| Command Code | 31:24 | The PMC User defined Command Code 0x47 |`.

### 1.2. Команда 0x47 — PMC User Defined Command Register **[пак]**

Единственная команда, раскладка которой в паке приведена полностью.

| биты | поле |
|---|---|
| 0 | Flash — сбросить PMC User Define FIFO |
| 1 | Last — записать содержимое FIFO событием PMC |
| 2 | Load uCode Cfg — загрузить «PMC Allowed Code» |
| 7:3 | резерв |
| 15:8 | Type — значение User Define Type |
| 17:16 | UCode Core Write Command: 00 запретить core write в PMC; 01 коды региона 1; 10 коды региона 2; 11 все коды |
| 23:18 | резерв |
| 31:24 | код 0x47 |

Хост включает захват в wil6436 так: `ucode_event_en` (0x88607c бит 26) = 1; локальная запись
`0x47000004 | (1<<16)`; диапазоны кодов — в `MAC_SXD_EXT.PMC_UCODE_WR_RANGE_0.sxd_pmc_start_1/end_1/start_2/end_2`.
Код 0x47 в образах 4.1 и 6.2 не встречается.

### 1.3. Бит 31 — событие PMC

**[пак]** Комментарий пака: в wil6436 старший бит core write больше не управляет записью в PMC, так как
расширяет диапазон адресов; вместо этого задаются два диапазона кодов. Следовательно, в Sparrow
(4.1/5.2/6.2) бит 31 означает «записать это слово событием PMC» с аппаратной меткой времени.

**[код]** Отправки с битом 31 в микрокоде 6.2 — отладочные сигнатуры (код 0x00 с меткой PMC):

| адрес | место | слово |
|---|---|---|
| 0x926676 | `uc_sysassert`+0x5e | 0x80eeeeee |
| 0x93691c | `txrx_api_step_c`+0x44 | 0xc0adc0ad |
| 0x92eba0 | — | 0x80aaab20 |
| 0x93cc7e | сразу после `handle_pmc_triggers(-1, 0)` | 0x80aaab02 |

В 4.1 такие отправки есть в `uc_sysassert` и `ps_awake_peer__build_evt`; в карте кодов они учтены как «0x80»
(не отдельный код) и на стенде не наблюдались — это аварийные метки.

Установка бита 31 в интересующей отправке превращает её в событие PMC, читаемое с хоста штатной записью
PMC, без изменения логики микрокода **[гипотеза]** (не опробовано).

## 2. Журнал r25

**[код]** Каждая отправка сопровождается записью в кольцо:

    mov   r32,rX          ; отправить в MAC
    st.ab rX,[r25,0x4]    ; положить в журнал, указатель += 4
    bclr  r25,r25,0xa     ; сбросить бит 10 -> обёртка по 1024 Б

В микрокоде 6.2: `mov r32,…` — 1028, `st.ab …,[r25,0x4]` — 1025, `bclr r25,r25,0xa` — 1025, то есть
журналируются практически все команды.

* Кольцо — первый килобайт `blob_uc_data` (данные микрокода, host 0x940000, см. `sparrow_fw_mapping`
  драйвера), 256 слов = 256 последних команд **[железо]**.
* Указателя записи в памяти нет; голова ищется сравнением соседних снимков.
* Слова, записанные в порт с хоста, в журнал не попадают: журнал ведёт сам микрокод (`st.ab [r25]`) **[железо]**.
* В простое кольцо заполнено одним значением `0x4d000005` — непрерывное чтение TSF **[железо]**.

## 3. Метод

### 3.1. Снятие кольца

* Чтение `blob_uc_data` штатным debugfs, без патчей прошивки и драйвера: на узле цикл
  `dd bs=1024 count=1`, разбор на хосте `SparRAW-tools/…/wil_mac_ring.py`. Темп ~250 снимков/с (4 мс на снимок).
* `window()` ищет окно новых слов по изменившимся позициям и возвращает третьим элементом признак
  надёжности. Переполнение определяется по разрыву изменений на много кольцевых кусков (калибровка:
  одно окно — 67 переходов, два — 21, три и больше — ненадёжно). Позиции без изменения не печатаются
  как команды; результат — **нижняя граница** числа команд. Логика поиска окна проверена на 2000 случайных
  прогонов (0 ошибок).
* Слепые зоны: команда, повторившая то же слово в ту же позицию, не видна; переполнение (полный оборот
  между снимками) теряет порядок. Потери сосредоточены в однородных состояниях (простой, повтор
  0x4d000005) и в переполнениях (~4 % переходов). Признак слепой зоны — мало различных значений в снимке
  (в `ring2-ap.bin` — 1 различное из 256). «Тихий» переход чаще означает отсутствие команд (микрокод ждёт
  события): трасса маячащей AP, 900 снимков — 596 команд, 39 переполнений, 820 тихих переходов (91 %),
  ~17 команд на интервал BI.

Пересчёт исправленным `window()`:

| трасса | до исправления | после | переполнений | тихих переходов |
|---|---|---|---|---|
| r-idle2.bin | 3820 | 718 | 43 | 832 |
| ring2-ap.bin | 10796 | 3480 | 92 | 1619 (из 1799) |
| ring2-sta.bin | 15810 | 886 | 106 | 1641 |

Частоты, собранные до исправления (в т.ч. «1939 команд за ~7 с при активном скане, 24 кода»; «AP 10796 /
станция 14666 команд, 47/33 кодов»; «108 794 команды в шести трассах, 62 кода»; «рестарт 32301 команда»),
годятся только как свидетельство «код встречается в таком-то состоянии». Действующие числа — в
`4.1/ref/MAC-CMD-MAP.txt` и `4.1/ref/MAC-CMD-PROFILE.txt`.

Практические ограничения стенда:

* под нагрузкой кольцо оборачивается почти каждый снимок (300 снимков — 67 тыс. команд при пределе 76.8 тыс.),
  сравнивать можно только доли кодов;
* длительное снятие (900 снимков) одновременно с iperf3 ронял станцию (`Device timeout (-62)`, лечится питанием);
  нагрузка без снятия и 300 снимков под нагрузкой проходят. Под нагрузкой снимать короткими сериями;
* перед установкой образа сверять версию `wil_fw_swap.sh` на узле: старая (4545 Б вместо 4973 Б)
  перезагружает драйвер, и `rmmod wil6210` зависает в состоянии D.

Образы при снятии: собственная сборка 4.1 без правок (`make fw`, md5 514ad929…, побайтово равна вендорской);
сборка с перехватами `build/wil6210-selfbuilt.fw` (348084 Б, md5 03549b72, CRC 0xe93744a6).

### 3.2. Статические места отправки

`SparRAW-tools/…/mac_cmd_sites.py` → `4.1/ref/MAC-CMD-SITES.txt` (также `6.2/ref/MAC-CMD-SITES.txt`): для каждого
`mov r32,…` небольшой интерпретатор регистров в пределах блока (`add/add1/add2/add3`, `or`, `and`, `xor`, `bset`,
`bclr`, `bmsk`, `asl`, `lsr`, `ror`, трёх- и двухоперандные формы) восстанавливает слово. Категории:
точное значение; база+индекс (`(0x52+idx)<<24`); «вероятно» (`A|X`, старший байт A, X не ограничен —
помечается `0xNN?????`); неизвестно. Всего 826 мест; точных 553, база+индекс 2, вероятных 168; неизвестных 56
после учёта цепочек `bset` и `or` двух неизвестных. Мест в коде имеют 77 кодов.

Приёмы, без которых коды не восстанавливаются:

* код набирается битами: `bset 0x19; bset 0x1b; bset 0x1d` = 0x2a, `bset 0x19; bset 0x1c; bset 0x1d` = 0x32,
  `bset 0x18; bset 0x1a; bset 0x1c` = 0x15;
* константы, материализованные сдвигом (`mov r2,0x14; asl r2,r2,0x18` = 0x14000000) — 42 места; это не
  база+индекс;
* `or` двух неизвестных: старший байт берётся от половины, несущей код.

Источник невосстановленного значения (116 отправок до доработок): `bset` 46, арифметика/сдвиг 41, `or_s` 14,
`bmsk` 6, `asl` 2.

Известные дефекты интерпретатора:

* условные инструкции применяются безусловно (470 предикатных в ucode; на 9 местах пара `mov.ne`/`mov.eq`
  пишет один регистр). Пример 0x92323e: железо шлёт и `0x18000000`, и `0x18001000`, в карте только второе;
* точки слияния не учитываются (11 отправок на цели перехода). 0x93392c: в карте 0x00, но через тот же
  `mov r32` уходит и `0x27003f00`;
* `--seg fw` с умолчаниями `--lo/--hi` даёт неверный результат;
* консервативные: регулярка `WRITE` считает записью `cmp`/`st`/`bbit`; `bl` и `pop_s` не инвалидируют
  caller-saved регистры.

### 3.3. Прочие инструменты

* `mac_cmd_infer.py` → `4.1/ref/MAC-CMD-INFERRED.txt` — вывод неизвестной отправки B по соседу: если в блоке
  подряд идут A (известна) и B, а в трассе за A стабильно следует V, то B = V. Достоверно только при
  единственной в образе опорной отправке. Самопроверка: независимо выведено `0x92b9a4 = 0x40000020`.
* `mac_cmd_profile.py` → `4.1/ref/MAC-CMD-PROFILE.txt` — доля кода на 1000 команд в семи состояниях
  (AP маячит, AP под нагрузкой, станция в покое, станция под нагрузкой, активный скан, переподключение, рестарт).
* `mac_cmd_fields.py` → `4.1/ref/MAC-CMD-FIELDS.txt` — сдвиги и биты полей параметра для 75 кодов (приложение А).
* `mac_lr_reads.py` → `4.1/ref/MAC-LR-READS.txt` — разбор локальных чтений (§7.3).
* `mac_cmd_map.py` → `4.1/ref/MAC-CMD-MAP.txt` — сводная карта: код, наблюдения, места, частые параметры,
  уровень обоснования. Словарь проверяется на дубликаты ключей.

## 4. Запись в порт с хоста

**[железо]** Запись в 0x886dc8 через debugfs `mem_write` проходит и читается обратно (0x00abcdef, 0x00123456,
0x1d00a000), маяк жив, но аппаратный автомат слово **не исполняет**. Опыт (baseline → опыт → откат → baseline):

| шаг | действие | результат |
|---|---|---|
| baseline | — | 0x886d64=0x64, 0x886dc0=0x19000, медиана интервалов DTI 102401 мкс |
| опыт | 0x886dc0 = 0x32000 (204800 мкс), 0x886dc4 = 0, затем 0x886dc8 = 0x0d000006 | 0x886d64 = 0x64, медиана 102405 |
| контроль | 0x886dc8 = 0x1d00a000 | порт хранит записанное |
| откат | — | медиана 102401 |

Отправка безвредных чтений 0x4d000005 / 0x4d000000 с хоста и сравнение `blob_rgf` дали 82 и 77 различий при
контроле без команды 80 — фоновая динамика. Управлять MAC с хоста через порт команд нельзя: триггер —
запись из ядра ARC в `r32`.

## 5. Пространство кодов

* **[код]** `mac_cmd_sites.py` по обеим версиям: 4.1.0.1000 — 77 кодов, 6.2.0.1000 — 77 кодов, общих 77,
  различий нет. Подтверждено независимым прогоном. Набор кодов — аппаратный интерфейс кремния Sparrow;
  `sxd_hal__*` (`sxd_hal__mac_select_indexed`, `sxd_hal__mac_write_indexed`, `sxd_hal__select_qset_group`,
  `sxd_hal__write_qset_field`) — программная обёртка. Знание, полученное на 4.1, переносится на 6.2 без изменений.
* Пространство плотное, 0x00..0x68; соседние коды обслуживают соседние регистры одного узла
  (0x04/0x05 и 0x42/0x43 — BRP/РЧ, 0x2a/0x2b — маяк, 0x3a/0x3b — цепь РЧ, 0x4f/0x50/0x51 — GP-таймеры 0..2,
  0x52..0x54 — регистры GP0..GP2, 0x67/0x68 — группа GP-таймеров).
* Родство видно по раскладке полей: у 0x2a и 0x2b сдвиги 6, 14, 15; у 0x16/0x17/0x1b — сдвиги 16, 8 и биты 0, 4, 5.
* Формулы «код ← адрес» нет (Замечания).
* В `4.1/ref/MAC-CMD-MAP.txt` 79 кодов (статические плюс наблюдённые без места, 0x80 — метка PMC, не код).

Вычисляемые коды (44 места со сдвигом на 24, у 33 база дальше шести инструкций):

| база | где | смысл |
|---|---|---|
| 0x52+idx | `sxd_hal__mac_select_indexed` (`add r0,0x52; asl r0,r0,0x18`), `sxd_hal__mac_write_indexed` (`add1 r3,r14,0x29; asl r3,r3,0x18` = r14+0x52, ARC `add1` = rb + rc<<1) | регистры GP0..GP2; парная `mov r7,0x49000000; bset r2,r7,r6` с битом idx+6 |
| 0x4f+idx | — | GP-таймеры 0..2 |
| 0x9+idx | `mac__program_qset_slots`, `tx__pick_slot_for_peer` (0x924e0e), `txrx_api_step_c` (0x931a20) | маска слотов (§7.6) |
| 0x1+idx | `nav_db__update`, `tx_rate_select_and_program` | — |

## 7. Коды подробно

### 7.1. 0x00 — метка трассировки **[железо]**

0x00 ничего не делает в MAC; параметр — идентификатор точки. Пак 11ad косвенно называет 0x00 «NOP»
(комментарий «Range1 = [NOP, NOP]» при нулевых start/end). Отправка не сопровождается ожиданием события.

| параметр | место |
|---|---|
| 0xcaf662 | `bi_ap_mon__aw_on_bhi_to_aw` (0x921c46) |
| 0xcaf661 | `bi_ap_mon__aw_on_bhi_to_dti` (0x921c76) |
| 0xcafcaf, затем 0x00f001 | `l1_task__entry` (0x9297a8 = 0x0000f001, вывод по соседству, 58/58) |
| 0xcafcaa | `l1_task__entry` |
| 0xcaf220\|idx (наблюдалось 0xcaf223) | `bi_ap_mon__aw_event` |
| 0xcaf110\|idx (0xcaf112), 0x9312c8 | `bi_ap_mon__dti_event` |
| 0xcaf000, 0xcaf001 | `bi_ap_mon__bti_event` |
| 0xeeee0b, 0xeeee09, … | маркеры 0xeeeeNN |

Под нагрузкой доля меток растёт: 15.2 → 87.4 на 1000.

### 7.2. 0x02 — маска ожидаемых событий

Параметр всегда битовая маска. Сопоставление каждой отправки с ближайшим последующим местом ожидания
(64 пары): бит 14 → busy2 (14/16), бит 15 → tx_end (11/12) — надёжны; бит 12 → rx_frame (10/16) — статистика
**[профиль]**. Самый массовый код (100 мест).

### 7.3. 0x1d и 0x4d — локальное чтение **[железо]**

Идиома: `0x1d` правит **один полубайт** теневой копии селекторов (`[gp,-0x44]`), после трёх тактов задержки
результат виден в регистре r36..r56. Группа в `MSXD_LR_RGF` = регистр результата, индекс в группе = значение
селектора. `mac_lr_reads.py`: 69 чтений разобрано, 67 названы вендорским файлом; имена совпали с
независимыми именами по лог-строкам:

| блок | регистр |
|---|---|
| `bi_window_timing_update` | BI_COUNTER |
| `mac_counter__program_3009` | COUNTER_EVENT_STATUS |
| `uc_wait_direct_tx_ready` | DIRECT_TX_CMD_STATUS |
| `queue_sel__get_qset4` | QUEUE_SEL_FOUND_SET1_4_R41 |
| `bap_q_avail__check` | BAP_Q_AVAIL |
| `rfc__issue_cmd_10`, `rfc__issue_cmd_20` | RFC_SWITCH_ERROR_STATUS |
| `abft_responder_worker` | LFSR_VAL |
| `hw_modes_mac__switch_core` | PHY_SIGNALS |

`0x4d` — чтение фиксированной группы R55 в r55 одним словом: селектор 0 = `SIFS_CNT`, 5 = `G2_TSF_LOW`
(`uc_read_tsf_lo`), 0xa = `GP_CLK2_TIMER` (`abft__arm_response_window`). Селектор 5 подтверждён трижды:
имя `uc_read_tsf_lo`, индекс [5] в файле регистров, 1204 наблюдения в простое.

Выбор LFSR (`bti_worker__bti_transmitter_beacon_sweep_flow`, 0x923e74):

    or  r6,r6,0x1d020000   ; селектор [19:16]=2 -> LFSR_VAL
    mov r32,r6
    nop nop nop            ; задержка конвейера
    mov_s r3,r47           ; значение ГПСЧ

Другие наблюдаемые селекторы: `0x1d284320` (перед 0x2a/0x2b и в передаче маяка), `0x1d230020` (цикл опроса
вокруг 0x13), `0x1d280320` (0x92431c, вывод по соседству, 7/7), `0x1d23d120` (0x9296a6, 0x92c92e, «вероятно»),
`0x1d000300` и 0x1d:010000 (селектор 1, `ucode_cmd__bi_config`).

### 7.4. Режимные коды: 0x06, 0x36/0x38/0x3c, 0x37, 0x1f

Блоки `mac_mode_program_a/b/c`, `mac_mode__switch_core_and_rf`, `mac_mode__switch_after_ppdu` прошивают
регистры MAC фиксированной последовательностью констант; общий хребет:

    1f:006000  38:000300  36:00003f  06:0001NN  37:000005  37:000002

* **0x06 — селектор режима** **[железо]**: AP маячит — 0x000103 (67 %), станция — 0x000000 (74 %), активный
  скан — 0x000210 (66 %); у передающей станции 0x101/0x210, не 0x103. Значение 0x103 — маячный режим;
  0x101 — переходный. 0x210 чаще у станции под нагрузкой (30.4/1000), чем при скане (7.7), и в статике его нет.
* **0x36/0x38/0x3c**: у маячащей AP 0x38/0x200/0x200 (88 %); у станции, при скане и у передающей станции —
  0x3f/0x300/0x300 (100 %). Карта формулирует как «различает покой/нагрузку, а не роль» (Замечания).
* **0x37** — в конце каждой процедуры парой 0x05, 0x02 («применить»); 0x20 — 136 раз у AP и один раз у станции.
* **0x1f** — маски 0x000601, 0x003000, 0x006000; распределение по ролям одинаково. 0x601 преобладает у маяка и
  в простое, 0x6000 — при передаче данных, 0x3000 — везде. Имя блока `mac__program_rf_mode`; режим РЧ /
  подготовка RX (`rx__switch_to_rx_mode`).
* **0x14** — значения 0x7, 0x100, 0, 2, 0x400; по ролям не разделяется.
* **0x01** — `mac_mode__switch_sequence`, `bi_mode_init_substep`.

### 7.5. Маячные коды: 0x2a/0x2b, 0x2d, 0x3f

**0x2a/0x2b** — `bi_ctrl__program_mac_bcon`, отправки 0x9332ac и 0x9332c4 **[код]**. Поля из `g_bi_ctrl_mgr`
0x80142c (байты +0, +1, +2, +5) и глобалы `[gp,0x80]`, `[gp,0x84]`. Код 0x2a собирается `bset` битов 25, 27, 29
поверх флага, сдвинутого в бит 6; 0x2b — `or` с 0x2b000000. Идут строго парой 0x2a → 0x2b, перед парой
`0x1d284320`, после — `0x14000100` (`bi_manager_rx_step`). При смене периода маяка 0x2b: остаток 0x201
постоянен, поле [0x80142c+1] принимало 0, 4, 8, 85 — динамика, не период. На железе независимо не проверены.

**0x2d — поле Sector Sweep 802.11ad** **[код]**, источник 0x935d06 в `bcon_txss_sweep_step`:

    mov r1,0x801c9c
    or  r2,r17,0x2d000000
    ldb r3,[r1,0xc] ; asl r3,r3,1      -> биты 1..9
    ldb r0,[r1,0xd] ; asl r0,r0,0xa    -> биты 10..15
    ldb r1,[r1,0xe] ; asl r1,r1,0x10   -> биты 16..23

| биты | поле SSW |
|---|---|
| B0 | Direction (из r17) |
| B1-B9 | CDOWN (счёт вниз до нуля) |
| B10-B15 | Sector ID |
| B16-B17 | DMG Antenna ID |
| B18-B23 | RXSS Length |

На 243 наблюдениях CDOWN убывает 9 → 0, Sector ID растёт 54 → 63, сумма 63. Байт [0xe] несёт два поля.
`bcon_txss_sweep_step` @0x935a4c вызывается из 0x9240d4 (внутри `bti_worker__bti_transmitter_beacon_sweep_flow`)
и из 0x936af0. Доля 0x2d падает под нагрузкой (16.0 → 0.6 на 1000) вместе с 0x49/0x54/0x68 — код маячного цикла.

**0x3f — TX/RX-вектор, биты 8..15 = Sector ID** **[код]**:

    935d40  mov_s r0,0x801c9c
    935d46  ldb_s r1,[r0,0xd]     ; тот же байт, что Sector ID в 0x2d
    935d4a  asl_s r1,r1,0x8
    935d4c  or    r0,r0,0x30
    935d5a  or    r0,r16,0x3f000000

Параметр вида `0x00NN30`; при маячении поле гуляет (совпадает с Sector ID из 0x2d в той же трассе), при передаче
данных фиксировано: 0x0a у AP, 0x08 у станции (сектор, выбранный на пира). 0x3f шлётся также из приёмных и
режимных блоков. Значение 0x3f000b30 выведено по соседству для 0x92308e, 0x9236b4, 0x92aa6c, 0x92bba0, 0x92da66,
0x92de44, 0x92e5ec, 0x92fc54, 0x9335ac (все «вероятно», 12/14).

### 7.6. GP-таймеры и r54: 0x49, 0x4f..0x54, 0x67/0x68

* **0x49 — квитирование битов событий r54** (EVENT4_STATUS) **[код]**. Формула из `sxd_hal__mac_write_indexed`:
  `mov r7,0x49000000; bset r2,r7,r6`, r6 = idx+6. Биты r54: 4 = `service_period_0`, 6/7/8 = `gp0_end_ind`/
  `gp1_end_ind`/`gp2_end_ind`, 15 = `ext_gp_0_1_2_end_ind`, 16 = `ext_gp_3_4_5_end`, 17 = `ext_gp_6_7_8_9_end`.
  Наблюдались одиночные биты 6, 7, 8 и 15. По 0x49 видна работа таймеров окон BI без патча:

  | состояние | квитирования |
  |---|---|
  | AP маячит | ext_gp_0_1_2_end ×27, gp2_end ×23, gp0_end ×18, gp1_end ×14 |
  | станция | gp2_end ×73, gp0_end ×60, ext_gp ×55, txss_end+gp0/1/2 ×20 |
  | AP под нагрузкой | gp0_end ×52, txss_end+gp0/1/2 ×49 |

  (счёт до исправления `window()`).
* **0x52/0x53/0x54 — регистры GP0/GP1/GP2** (0x52+idx, парная 0x49 с битом idx+6) **[код]**.
* **0x4f/0x50/0x51 — GP-таймеры 0/1/2** **[гипотеза]** (обоснование в карте не записано).
* **0x67/0x68 — группы GP-таймеров** **[код]**: `sxd_hal__select_qset_group` (0x925034…0x925058) разбивает индекс
  порогами 6 и 10 и шлёт 0x49010000 / 0x49020000 (биты 16/17 r54); группы 0-2 / 3-5 / 6-9. 0x68 — выбор группы,
  индекс в битах 20..23; 0x67 — данные (`sxd_hal__write_qset_field`). Имена блоков `*_qset_*` отражают
  не очереди, а группы таймеров.
* Коды 0x49, 0x52, 0x53, 0x54, 0x67, 0x68 высоки в покое и падают почти в ноль под нагрузкой; 0x50/0x53/0x54/0x67/0x68
  смещены к маячащей AP.

**0x09..0x0c — маска слотов** **[код]**. Цикл в `mac__program_qset_slots` (0x928308):

    mov lp_count,0x4        ; четыре набора
    add r1,r13,0x9          ; код = 9 + индекс
    asl r1,r1,0x18
    ldb r2,[0x800ac8+idx]   ; число слотов (add2_s r0,r0,r13: база + индекс*4)
    bset r0,r0,r2 ; sub r0,r0,1   ; маска 2^N - 1
    or  r0,r0,r1 ; mov r32,r0

Таблица 0x800ac8 в образе нулевая, живьём (host 0x940ac8) — 4, 4, 4, 4 → маска 0xf. Параметр 0x1f (5 слотов)
у 0x0b идёт из `tx__pick_slot_for_peer` (0x924e0e: `add r0,r14,0x9; asl 0x18; or маска`); то же в
`txrx_api_step_c` (0x931a20). 0x0b виден только под нагрузкой (0.3 и 2.6 на 1000 на обеих сторонах).

**0x0f** — в `queue_sel__get_qset4` строгая тройка: 0x0f000001, затем 0x1d с селектором 1, через три такта чтение
r41 = `QUEUE_SEL_FOUND_SET1_4_R41`. Стоит в стоковом микрокоде `0x9311fe mov_s r3,0xf000001` внутри
`bi__decide_beacon_kind` под условием `bcon_kind != 0`: число 0x0f000001 в кольце = число вызовов
`bi__decide_beacon_kind`.

### 7.7. 0x30 — задержка маяка **[железо]**

Отправка 0x923ea8 в `bti_worker__bti_transmitter_beacon_sweep_flow`:

    0x923dfc  mov r13,0x801438   ; g_bi_cfg_params
    0x923e04  ld  r7,[r13]
    0x923e0c  cmp r7,0x2         ; bi_mode == BI_TX_DISCOVERY_BCON ?
    0x923e14  bne 0x00923f4c     ; иначе в обход
              ld r10,[r17] ; cmp r10,0 ; bne 0x923f4c   ; второе условие
    0x923e74  or  r6,r6,0x1d020000   ; селектор 2 = LFSR_VAL
    0x923e92  mov r3,r47             ; аппаратный LFSR
    0x923e94  mulu64 r3,0xbd         ; x189
    0x923e98  mov r0,mhi             ; старшая половина (метод Лемира)
    0x923e9c  add r15,r0,0xa         ; +10 -> [10, 198]
    0x923ea0  or  r2,r15,0x30000000
    0x923ea8  mov r32,r2
    0x923edc  bl  set_tsf_event

Источник случайности — аппаратный LFSR регистрового файла MAC; деления нет. Тот же LFSR_VAL читает
`abft_responder_worker` (слот ответа в A-BFT). В обходе 0x923e1c…0x923f4c лежат также запись в лог, отправка
0x1d020000, `uc_read_tsf_lo`, приращение накопителя [0x801438+0x18] = 0x801450 и вызов `set_tsf_event` @0x923edc —
при закрытом гейте аппаратный компаратор TSF не взводится. Между 0x923f4c и вызовом развёртки 0x9240d4 есть
не менее четырёх условных выходов: 0x923f54, 0x923f78, 0x924004 (порог 30000 мкс), 0x924068 (бит 14 r42).

На стенде штатно `g_bi_cfg_params.bi_mode` = 1, и 0x30 не уходит (свыше 140 тыс. команд, семь состояний плюс
рестарты). Запись `0x941438 = 2` (host-адрес; по линкерному 0x801438 запись бесполезна) — 0x30 идёт: значения 66,
197, 62, далее шесть разных в 58…182; связь не рвётся. При этом записи `MAC_MON [DTI]` в логе прошивки
перестают появляться и возобновляются при возврате 1 (причина не установлена). Второй гейт на том же поле —
заглушка `trigger_bhi` @0x930564 (§8.1): при 2 автомат идёт BHI→DTI.

Сборки с перехватом развилки `bi__decide_beacon_kind`:

| сборка | 0x30 | 0x0f000001 | 0x2d | команд |
|---|---|---|---|---|
| `make fw DEFS=-DFORCE_BEACON_SWEEP=1` (348092 Б, CRC 0xae11d7f5) | 0 | 8 | 112 | 8594 |
| `SWEEP_ON_KIND1` | 0 | 1 | 48 | 4798 |

В обоих случаях `MAC_MON [DTI]` на месте (интервалы 102984, 101813, 102402). 8 вызовов × ~14 секторов = 112 — развёртка
шла из перехваченного места; отсутствие 0x30 при этом объясняется вторым условием `ld r10,[r17]` **[гипотеза]**.
Цепочка вызовов: `bi_ap_mon__bti_event` @0x931154 → `bi_manager__kind_switch` @0x9289e4 (вызов 0x9289e4 →
`bi__decide_beacon_kind` @0x9311a4) → @0x93125c `bti_worker__bti_transmitter_beacon_sweep_flow` @0x923de0 или
@0x931250 `bti_transmitter_bi2_flow` @0x923c74. `ctx->kind` — аргумент события: из l1_task передаётся 0, и на
0x93124c `brne r0,0x1` уводит в `beacon_sweep_flow`. Условие в перехвате (дизассемблер объектника):
`mov r0,r41; btst_s r0,0x1e` (бит 30 = событие маяка); `ld_s r0,[r13,0]; breq r0,0x1` → обход подмены.

### 7.8. 0x08

Параметры 0x924f00, 0x924f20, 0x924000 попадают в диапазон кода (`direct_tx__push_payload`,
`uc_wait_direct_tx_ready`), но место 0x924e5a собирает составное слово **[код]**:

    ldb r1,[sp,0x2] ; asl r1,r1,0x4
    ldb r0,[sp,0x3] ; asl r0,r0,0x6
    ld  r0,[gp,-0xd8] ; and r0,r0,r2   ; маска из глобала и [0x800994+8]

### 7.9. 0x13, 0x34, 0x15, 0x32, 0x33

* **0x13** — 0x933f6a в `tx_initiator__build_tx_vector`, код набран `bset` битов 24, 25, 28. Параметр 0x002002
  (115 раз при переподключении), зажат между двумя `0x1d230020` — цикл опроса при установлении связи.
* **0x34** — 0x924ede, единственная неизвестная отправка блока `direct_tx__program_cmd34`; в трассе за соседкой
  0x33000001 идёт 0x34xxxxxx.
* **0x33** — `direct_tx__issue_cmd_33`, значение 0x33000002.
* **0x15** — у маяка всегда 0xffff; при передаче данных 0x22, 0x26, 0. Не AID адресата (у подключённой станции AID = 0).
* **0x32** — только 0x000000 и 0x000001, почти поровну, в `mac_mode__wait_ppdu_and_kick` (`_e`), `rx_flow_step`,
  `rx_flow__handle_frame`; появляется только с трафиком у AP, высок у станции в покое (106.9 на 1000).

### 7.10. 0x1e

Посылает только 0x010004 и 0x010001 из блока 0x93160c, вызываемого один раз из `uc_main_init` до начала любой
трассы. Рядом тот же блок пишет `0x886d88 = 0x0c0a0f1e` **[железо]**, регистр не опознан. Тайминги IFS
передаются LMAC-командой 0x00 body+0x30 ([LMAC-PROTOCOL](LMAC-PROTOCOL.md)); имя блока
`bi_mode__program_ifs_timing` не отражает назначения.

### 7.11. РЧ-контроллер: 0x3a/0x3b, 0x40, 0x41, 0x42/0x43

`brp__write_reg_pair` (0x92bcac) **[код]**:

    extw_s r1,r1           ; младшие 16 бит
    or  r1,r1,0x42000000
    mov r32,r1
    lsr_s r13,r13,0x10     ; старшие 16 бит
    or  r13,r13,0x43000000
    mov r32,r13

0x42/0x43 передают одно 32-битное слово половинами (у 0x42 — 0xaa, 0xdc, 0xbb; у 0x43 всегда 0). 0x41 —
команда РЧ-контроллеру: `or r13,r13,0x41000010`, перед ней ожидание готовности `bbit1 r1,0x11` по r47; младший
байт — операция 0x10/0x20 (`rfc__issue_cmd_10`, `rfc__issue_cmd_20`). 0x40 всегда сразу после `0x3b000006`,
параметр 0x000020: 0x92b9a4 `bset r0,r13,0x1e` (r13 | 0x40000000, r13 — аргумент).

## 9. Связь с регистрами и параметрами

### 9.1. Период маяка

Период BI командой MAC не задаётся **[железо]**: при `wifi reload` с `beacon_int` 100 и 200 TU (10471 и 21830 команд)
ни один параметр не изменился вдвое (кроме метки 0x00 0x0002f2 → 0x0005e4 — совпадение). Ячейки, пропорциональные
периоду (серия 100/150/200/250 TU, монотонный рост, отношение v(250)/v(100) в 2.4…2.6):

| линкерный | host | BI=100 | BI=200 | смысл |
|---|---|---|---|---|
| 0x800928 | 0x940928 | 100028 | 202427 | |
| 0x801434 | 0x941434 | 102400 | 204800 | `g_bi_ctrl_mgr.beacon_interval_usec` (+0x08) |
| 0x801e40 | 0x941e40 | 98513 | 204798 | вычисленные окна |
| 0x801e48 | 0x941e48 | 102394 | 204794 | |
| 0x886d18 | 0x886d18 | 102392 | 204792 | период − 8; пара 0x886d18/0x886d1c |
| 0x886d64 | 0x886d64 | 100 | 200 | регистр MAC, период в TU |
| 0x886dc0 | 0x886dc0 | 102400 | 204800 | защёлка аргумента 0x0d |
| 0x8002c0 | 0x9002c0 | 100 | 200 | |
| 0x804558 | 0x904558 | 102490 | 204889 | |
| 0x8064b0 | 0x9064b0 | 100 | 200 | конфигурация BSS |
| 0x8064d8 | 0x9064d8 | 100 | 200 | |

Также 0x8403fc (fw_peri) 102400 → 204800 и 0x854e08 (рядом с MAC_MON) 63 → 126.

* **0x886dc0/0x886dc4** — 64-битная защёлка аргумента команды 0x0d: пишется парой на 0x8e499e, затем в порт
  идёт `0x0d000006` **[код]**. Так же устроены пары 0x886d18/0x886d1c и 0x886d20/0x886d24.
* **0x886d64** пишет микрокод: `0x931798 st_s r1,[r0,0x64]` при r1 = 0x64 (100 TU). Обращается к нему блок
  `aw__compute_tbtt_from_hw`. Одиночная запись 0x886d64 = 200 с хоста останавливает маячный цикл
  (строки `L1_TASK PRE TBTT` исчезают, клиент отваливается); возврат 0x64 восстанавливает (102402 мкс) **[железо]**.
* **0x801434** читается в рантайме (0x93253e, 0x9219e2, 0x92ae64); два последних передают значение в 0x930494,
  которая пишет 0x886d18/0x886d1c. Запись 0x941434 = 204800 на лету период не меняет (102403 мкс); по линкерному
  адресу читается ноль.
* Запись 0x886dc0 = 204800 период не меняет (102405 мкс), значение держится.
* Согласованная запись 0x886d64=200, 0x886dc0=204800 и удвоенных 0x941afc/0x941b00/0x941b04 останавливает маяк;
  запись всех 11 ячеек значениями от BI=200 маяк не останавливает (0x886d64=0xc8, 0x886dc0=0x32000,
  0x886d18=0x31ff8 держатся), но период остаётся 102400 мкс. Штатно период меняет только `wifi reload`.
* Расписание BTI/AW/DTI от `beacon_int` не зависит: 0x802030..0x802077 (36 значений), 0x801afc = 41819,
  0x801b00 = 47800, 0x801b04 = 95600 не меняются при 100 → 200 TU; строится из `cfg[+0x07]`, `cfg[+0x0a]`
  (`bi_build_schedule_tables`). 0x801b04 не производная от 102400.
* Измеритель периода — интервалы `L1_TASK PRE TBTT` (лог микрокода) или `MAC_MON [DTI] start time` (лог прошивки).
  Штатный джиттер с компенсацией: 102401, 102396, 102985/101818 (пара = 2·BI), 204797, 307198; медиана 102402,
  ±586 мкс.

### 9.2. Тайминги MAC (такт 165 МГц) **[железо]**

`us_from_ticks165` @0x931c98 делит на 0xa5. `sifs_clk = 0x1ef = 495` → 3 мкс (`mov r1,0x1ef` @0x8ec10a),
`slot_clk = 0x339 = 825` → 5 мкс (`mov r0,0x339` @0x8d857e).

| регистр | живьём | смысл |
|---|---|---|
| 0x886d00 | 0x01730300 | SIFS 3 мкс + константа 0x0173 |
| 0x886d04 | 0x03400500 | slot 5 мкс + биты 22/24/25 |
| 0x886d08 | 0x0a000800 | SIFS+slot = 8 мкс, 2·slot = 10 мкс |
| 0x886d0c | 0x01000100 | RIFS 1 мкс, SBIFS 1 мкс |
| 0x886d10 | 0x35d | по коду ожидалось 0x100, писатель не установлен |
| 0x886d88 | 0x0c0a0f1e | пишет блок 0x93160c, не опознан |
| 0x886f70, 0x886f74 | 0x07d007d0 | предел TXOP 2000 мкс |

Предел TXOP программируется в 0x931cac. `short_txop_en` (LMAC 0x1e body+0x04 → `[gp,0x24]` = 0x80054c; запись
0x937076, чтение 0x931cac) сдвиг предела не включает: условие `cmp_s r3,0x0` @0x931cb8, `cmp.ne r0,0x0` @0x931cba,

`_mov_s r0,0x0`, r0 всегда ноль.

### 9.3. Прочие ячейки, найденные методом дампов

Метод — серия дампов `blob_fw_data`/`blob_fw_peri`/`blob_uc_data`/`blob_rgf` с фильтрами `wil_memscan.py`
(`increased`/`decreased`/`changed`/`unchanged`, `--monotonic`, `--ratio`); контрольный дамп в том же состоянии
отсекает динамику. `--min` отсекает по первому снимку (для счётчиков с нуля нужен `--min 0`); `--monotonic`
не учитывает переполнение 32/16 бит.

* **Канал** хранится индексом с нуля (0/1/2 для 58320/60480/62640 МГц): fw_data 0x8000b8, 0x8000bc, 0x8033dc,
  0x8042a8, 0x805984, 0x80648c, 0x806490, 0x8064b8, 0x8064ec; rgf 0x88941e; fw_peri 0x84d94b, 0x84de83, 0x84e3bb,
  0x84e8f3 (шаг 0x538 — RX-пул, [4.1/docs/STRUCTS](../4.1/docs/STRUCTS.md)).
* **SSID**: fw_data 0x80595e; fw_peri 0x846b32, 0x84aa56 (плюс плавающие копии — шаблоны кадров). Район
  0x8059xx…0x8064xx — конфигурация BSS (SSID, канал 0x805984 на 0x26 дальше SSID, период).
* **Время следующего TBTT**: 0x801ffc (кратно BI: 1650585600 = 16119·102400; приращения 307200 и 409600).
  Производные: 0x800724, 0x80090c, 0x800920, 0x801e2c, 0x801e50, 0x8027dc. Запись в 0x941ffc перезаписывается
  каждый BI (0x63dcd350 → 0x641db000 через 3 с).
* **Состояние связи** (1 → 0 → 1 станция): fw_data 34, fw_peri 81, uc_data 21, rgf 24 ячейки; среди них 0x801034 (1/0),
  0x80141c (255/8).
* **Активный скан**: 0x8008dc 0 → 1 (один короткий снимок, не закреплено); серия покой/скан — 70 различий в uc_data
  (16 мелких), 15 в fw_data (3 мелких): кластер 0x802340…0x802464 (шаг 0x14/0x18, 22/23 → 0) перед очередью
  событий 0x802470; 0x805b04 (24 → 0), 0x803dbc (31 → 32), 0x8000cc (2 → 3).
* **Роль интерфейса**: единой ячейки нет — 86 устойчивых различий в uc_data, 79 в fw_data, 88 в rgf.
* **Board-файл** в fw_peri: магия 0xBDF0BDF0 на 0x84f800, COMMON_RF на 0x84f858, PARAMETERS на 0x84ff50.

## 10. Замечания

* Код ≠ смещение/4 в AHB-окне MAC_SXD: совпадение 1 из 14 проверенных блоков.
* Раскладка полей команд не совпадает с раскладкой регистров чтения (241 регистр `MSXD_LR_RGF`, 0x2d не совпал ни
  с одним ни двумя полями из трёх): регистровые файлы записи и чтения независимы.
* 0x886dc0 — не регистр периода, а защёлка аргумента 0x0d.
* 0x49 квитирует события r54, а не выбирает наборы очередей; 0x67/0x68/0x52..0x54 — GP-таймеры.
* Имена `sends_pmc_mark_aaab20` / `sends_pmc_mark_aaab02` (6.2) неверны: команды 0x80 нет, это 0x00 с меткой PMC.
* Для 0x36/0x38/0x3c источники расходятся: по параметрам 0x200 только у маячащей AP, 0x300 у станции (в т.ч.
  передающей); карта `MAC-CMD-MAP.txt` пишет «различает покой/нагрузку, а не роль».
* Уровни обоснования в разных срезах: железо 5 / код 19–20 / место 9–16 / блок 2 / профиль 13–17 / слабо 22–31;
  действующий срез — шапка `4.1/ref/MAC-CMD-MAP.txt`.
* 0x2a/0x2b — только разбор кода: единственный опыт выводил поля из самой команды.
* 0x92b8f8 — не источник 0x2d: там `or r13,r13,0x3f000000`, `or` не даёт старший байт 0x2d.
* Блоки собственной сборки шлют только вендорские коды (`0x02000040` TSF_ARM, `0x0f000001`, `0x1d000300`).
* Адреса компаратора TSF 0x8022c0/0x8022c4 относятся к 6.2; в 4.1 по ним лежит другое.
* Блок 0x92a608 — `nav__remaining_time_us` (имя `bi__remaining_time_us` для него неверно), 0x92a5ec — `nav__refresh_state`.
* Прямых обращений к 0x84d9xx в листинге нет: база RX-пула вычисляется через регистр.

## 11. Не установлено

* Назначение кодов уровня «слабо» (31): 0x01, 0x07, 0x08, 0x12, 0x13, 0x14, 0x15, 0x1c, 0x1f, 0x20, 0x21, 0x23, 0x27,
  0x29, 0x31–0x39, 0x3a–0x3d, 0x4f–0x51, 0x56 и др.
* Регистр, который пишет кольцевой 0x1e; регистр 0x886d88; писатель 0x886d10 = 0x35d.
* Какое из двух условий гейта рандомизатора блокирует 0x30 в сборках с перехватом.
* Почему при bi_mode=2 записи `MAC_MON [DTI]` пропадают из лога.
* Какое ещё состояние (компаратор TSF, GP-таймеры) мешает горячей смене периода.
* Исполнение отправок с битом 31 как событий PMC на Sparrow не проверено.
* Таблицы расшифровки кодов в паке 11ad нет: в `fw/ucode_image_globals.xml` только образы данных (0xa36000..0xa3ffff —
  `g_dbg_dashboard`, 0xa70000..0xa7f1e0), полей `cmd/core/sxd` ноль; в 875 файлах утилит и драйвера упоминается
  только 0x47.

## Приложение В. Смежные результаты, полученные через кольцо и память

### В.1. Автомат BI (микрокод 4.1)

`l1_task__entry` (0x929738) — диспетчер по r0: `92973c breq_s r0,0,0x929788` (r0=0), `929740 beq_s 0x9297ee`
(r0=1 — ветка r42), `929744 beq 0x929900` (r0=2 — ветка r54). Событие 0 (DTI_TO_BTI) подаётся на 0x9298c4/0x9298c6
(`mov_s r0,0x0; bl bi_ap_mon_if__trigger`) под битом 4 r42 (`0x929886 mov r0,r42; 0x929888 bbit0 r0,0x4`). Ветка r54:

    929900  mov   r0,r54
    929902  bbit0 r0,0xf,0x929920   ; бит 15 = ext_gp_0_1_2_end
    929906  mov   r0,0x49008000     ; квитировать
    929916  mov   r0,0x4           ; AW_TO_DTI
    929918  bl    bi_ap_mon_if__trigger
    929920  mov   r0,r54
    929922  bbit0 r0,0x4,0x929942   ; бит 4 = service_period_0
    929926  mov   r0,0x49000010

AW→DTI ведут GP-таймеры (r54 бит 15), DTI→BTI — r42 бит 4. `bi_ap_mon_if__trigger` индексирует таблицу заглушек
0x800dd4 (шесть смещений от 0x920000: 0x104e4, 0x10524, 0x10548, 0x10564, 0x105a4, 0x105bc → 0x9304e4, 0x930524,
0x930548, 0x930564, 0x9305a4, 0x9305bc; с +0x18 — другая таблица), заглушка подставляет свой номер события:

| r0 | заглушка | событие | вызывающие |
|---|---|---|---|
| 0 | 0x9304e4 | 0 DTI_TO_BTI | `l1_task__entry` @0x9298c6 |
| 1 | 0x930524 (`mov r1,0x2`) | 2 BHI_TO_DTI | `bi_manager__kind_switch` @0x928a04, `bi_ap_mon__trigger_tail` |
| 2 | 0x930548 (`mov r1,0x1`) | 1 BTI_TO_ABFT | `bi_manager__enter_dti` @0x926884 |
| 3 | 0x930564 `trigger_bhi` | 3 BHI_TO_AW, при bi_mode==2 — 2 BHI_TO_DTI (`930578 ld r3,[0x801438]; 930580 breq r3,0x2,0x930598; 93058e mov r1,0x3`) | `bi_manager__enter_dti` @0x9268b4 |
| 4 | 0x9305a4 | 4 AW_TO_DTI | `l1_task__entry` @0x929918 |
| 5 | 0x9305bc (`mov r1,0x0` при r13==0) | 0 DTI_TO_BTI | `bi_manager__run_rx_flow_by_kind` @0x928784 |

Ещё один вызывающий — 0x9269a4 (`l1_bi_trigger_step`). Обработчики DTI_TO_BTI по `4.1/ref/SM-TABLES-UC.txt`:
BTI и DTI → `bi_ap_mon__bti_event`; AW → `bi_ap_mon__aw_on_dti_to_bti`; ABFT → `assert_bad_event`. По меткам
маячащей AP: `aw_event` ×9, `dti_event` ×9, `bti_event` ×2, `l1_task__entry` ×10. Подробно —
[STATE-MACHINES](STATE-MACHINES.md).

### В.3. Ответчик A-BFT **[железо]**

Структура `fui_abft_resp_ctrl_s` (ucode / host), задаётся LMAC-командой 0x23:

| адрес | поле |
|---|---|
| 0x80208c / 0x94208c | relaxation_period_cnt |
| 0x802090 / 0x942090 | abft_responder_mode: 0 UNASSOCIATED_ONLY, 1 ASSOCIATED_ONLY, 2 ALWAYS, 3 DISABLED |
| 0x802094 / 0x942094 | beacon_type: 0 NOT_DISCOVERY, 1 DISCOVERY, ≥2 ALL |
| 0x802098 / 0x942098 | relaxation_period (u16) |

Счётчики в структуре принятого маяка 0x801e68 (host 0x941e68): +0x1c отправлено, +0x1e повторы, +0x20 отказ по mode,
+0x22 по beacon_type, +0x24 по relaxation, +0x26 принято. Раскладка 0x801e68: +0x00..0x03 (пишет
`rx_flow__handle_frame`, читают `abft_responder_worker`/`abft_responder__tx_ssw`), +0x04..0x07 (`rx_flow__handle_frame`,
`bti__bi2_event_step`), +0x08/+0x09 (`abft_responder__tx_ssw`), +0x0c (`bti_worker__collect_bf_metric`), +0x10..0x15
(данные BF, `bti_worker_bi2_step`, `abft_responder_worker`/`_substep`), +0x1a (`bi_dti__kick_worker`), +0x1b флаг
«отвечать в этом A-BFT», +0x28/+0x2a (`mac_mode_program_c`).

Стенд: AP (mode 2, beacon_type 1 от `pcp_start`) — 0 отправлено, 19735 отказов по beacon_type; STA (0, 2 от
`lmac_ready`) — 1 отправлен, 1431 отказ по mode. Запись 0x942090=2, 0x942094=2, 0x942098=0 даёт у станции 22 ответа
SSW за 8 с. Предварительные гейты: `(BIC>>15)&0xF == 0` и `fss >= 4`. bi_mode 3 (`BI_TX_DIRECT_SINGLE_BCON`)
в 4.1 не реализован. WMI `DISCOVERY_START` 0x916 через debugfs `wmi_send` (`wil_write_file_wmi: 0x0916[0] -> 0`)
принимается, но конфигурация ответчика не меняется (путь P2P Find должен ставить ALWAYS + DISCOVERY через
`find_mng__add_bcon` и вызывать `mid__acquire_link` в состоянии SEARCHING); в логе прошивки следа нет (другие команды
видны, например «HOST CMD 0x00000820 … WMI_CFG_RX_CHAIN_CMDID»), но лог в опыте не обновлялся. Вероятно, нужна нагрузка
команды или предварительное состояние — сравнить с тем, что кладёт в mbox `l2mgr__start_discovery` **[гипотеза]**. Подробно — [WMI](WMI.md).
