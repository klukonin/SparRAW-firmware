# Соответствие механизмов прошивки IEEE 802.11ad / 802.11-2020

Какие механизмы DMG (802.11ad, вошедшего в 802.11-2016/2020) реализованы в прошивке,
где они в коде и чем прошивка отличается от стандарта. Адреса — 4.1.0.1000
(fw 0x8c…–0x8f…, ucode 0x92…–0x93…, данные ucode 0x80…, host-окно ucode 0x94…),
если не помечено **[6.2]**.

Метки: **[железо]**, **[код]**, **[пак]** (вендорские имена пака 11ad), **[гипотеза]**,
**[стандарт]** — по тексту стандарта.

Разделы о структуре BI, SLS, A-BFT, BRP, кластеризации и OCB сопоставлены по названиям
механизмов и полей без номеров пунктов (нумерация разнится между 802.11ad-2012 и
ревизиями 802.11-2016/2020). Раздел об интервале маяка станции опирается на IEEE Std
802.11-2020 с номерами пунктов.

## Структура интервала маяка

BI = **BTI → A-BFT → ATI → DTI**.

| стандарт | прошивка |
|---|---|
| BTI — точка (PCP/AP) передаёт DMG Beacon по секторам = **I-TXSS** | `bti_duration`, `bti_num_tx_bcon` (63 = развёртка) |
| A-BFT — состязательный период, **ответчики** делают R-TXSS | ответчик A-BFT, структура 0x802090 |
| ATI — Announcement Transmission Interval | «окно AW», `aw_duration`, элемент ID 157 |
| DTI — данные (CBAP и SP) | `dti_duration`, счётчики RTS/CTS/DTS |

## SLS — Sector Level Sweep

Четыре фазы: **I-TXSS → R-TXSS → SSW-Feedback → SSW-ACK**. Им соответствуют биты
маски классов кадра `0x801038`: бит 0 = SSW, бит 2 = SSW-Feedback, бит 3 = SSW-ACK.
Поэтому `txss__init_sweep_b` @0x93645e даёт ассерт на бите 3: SSW-ACK не может прийти
раньше Feedback, это нарушение порядка фаз.

## Поле Sector Sweep — источник 0x804020

Есть и в SSW-кадрах, и в DMG Beacon:

| стандарт | разм. | прошивка |
|---|---|---|
| **Direction**: 0 = передал инициатор, 1 = ответчик | 1 бит | бит 0 слова 0x804020 |
| **CDOWN** — убывающий счётчик, **0 в последнем кадре развёртки** | 9 бит | `zero_cdown` = r39 бит 15 |
| **Sector ID** | 6 бит | `sector_id` из 0x800fcc, → 0x801b2a |
| **DMG Antenna ID** | 2 бита | `antenna_id` → 0x801b28 |
| **RXSS Length** | 6 бит | поле DMG Capabilities, на железе 53 |

`CDOWN == 0` по стандарту — признак «развёртка встречной стороны закончена, дальше
своя фаза». Бит 1 маски 0x801038 соответствует ровно этому.

## Ролевой гейт SLS

В SLS две роли: **инициатор** и **ответчик**; поле Direction указывает, кто передал
кадр. Пока инициатор свипует, ответчик принимает квази-омни, и наоборот. Проверка в
`rx_funcs__handle_ppdu_report`
(`принять ⟺ (Direction==0 ∧ роль=ответчик) ∨ (Direction==1 ∧ роль=инициатор)`,
слово роли 0x800604 биты 5/6) — дословная реализация ролевой семантики стандарта;
BSSID в ней не участвует и участвовать не должен.

## A-BFT

Состязательный период сразу после BTI: **ответчики** делают R-TXSS, посылая
SSW-кадры в **случайно выбранном слоте** (случайность разводит коллизии между
несколькими ответчиками).

| стандарт (поля DMG Beacon) | прошивка |
|---|---|
| **A-BFT Length** — число слотов | `abft_length` (+0x0a конфигурации BI) |
| **FSS** — число SSW-кадров в слоте | `fss` (+0x07), на железе 0x0f |
| сколько BI до следующего A-BFT (точка может выделять A-BFT **не в каждом** BI) | `n_bis_abft` (+0x04), на железе 4 → измерено 2.44 окна/с. Механизм — уверенно, соответствие имени поля — менее уверенно |

По стандарту A-BFT служит тому, чтобы **неассоциированная** станция натренировала
луч с точкой **до** ассоциации. Вендорское значение по умолчанию
`abft_responder_mode = UNASSOCIATED_ONLY` — буквальное прочтение стандарта;
`ALWAYS`, которое включает режим OOB, — расширение за его пределы.

`relaxation_period` — вероятно, вендорская форма стандартного отката ответчика
(не получив SSW-Feedback, ответчик увеличивает счётчик неудач и пропускает несколько
интервалов до следующей попытки) **[гипотеза]**.

### Длительность слота A-BFT: таблицы по FSS **[код]**
Для числа кадров SSW в слоте (поле FSS, индекс таблиц — `cfg[+0x07]`, 12 значений)
ucode держит три таблицы u16. В 4.1 их строит `bi_build_schedule_tables` 0x927f00 при
запуске (в double), в 6.2 это готовые константы данных ucode:

| таблица | 4.1 | 6.2 | значение (N — число кадров, N = 5…16) |
|---|---|---|---|
| 1, мкс | 0x802030 | 0x80164c | `(N−1) + 14,9·N + 0,9`: 79…254 |
| 2, такты MAC | 0x802048 | 0x801664 | `12955 + 2624·(N−5)`: 12955…41819 |
| 3, такты MAC | 0x802060 | 0x80167c | таблица 2 + **5981** (4.1) / + **9281** (6.2) |

Константы совпадают с длительностями 802.11ad при такте MAC 165 МГц: шаг 2624 такта
= 15,9 мкс = TXTIME кадра SSW (14,9 мкс, control PHY) + SBIFS (1 мкс); 1485 тактов =
9 мкс = MBIFS; 3011,25 такта = 18,25 мкс = TXTIME кадра SSW-Feedback. Таблица 3 в 4.1 —
таблица 2 + MBIFS + SSW-Feedback + MBIFS, то есть конец слота A-BFT (aSSSlotTime без
времени распространения) по стандарту. В 6.2 к ней добавлено 3300 тактов = **20 мкс**
для каждого FSS.

Таблицу 3 читает `abft__arm_response_window` (обе версии): значение `GP_CLK2_TIMER`
(команда MAC 0x4d, селектор 0x0a) сравнивается с таблицей 3 — «ещё внутри слота».
Её же используют `abft_responder__tx_ssw` и `bf_gpc__program_mac_by_mode_b`. Итог:
4.1 закрывает слот почти по стандарту, 6.2 — на 20 мкс позже (запас на задержку
ответчика).

По 802.11-2020, 10.42.5.2: aSSSlotTime = aAirPropagationTime + aSSDuration + MBIFS +
aSSFBDuration + MBIFS; aSSDuration = (FSS − 1) × SBIFS + FSS × TXTIME(SSW),
aSSFBDuration = TXTIME(SSW-Feedback) (таблица параметров DMG MAC), MBIFS = 3 × aSIFSTime,
aAirPropagationTime = 100 нс, aSIFSTime = 3 мкс, aSBIFSTime = 1 мкс (табл. 20-30).
Значит, 4.1 недосчитывает 100 нс времени распространения (16,5 такта), 6.2 переходит
за конец слота на ~19,9 мкс. В 6.4 (патч `6.4/patches/0003`) таблица 3 = таблица 2 +
5998 тактов (36,35 мкс), полное значение стандарта.

Стенд **[железо]**: серия из 15 переподключений станции после перезапуска обоих узлов —
6.2: 15/15, 709–789 мс; с 0003: 15/15, 710–790 мс. Время подключения определяет в
основном `wpa_supplicant`, поэтому это проверка отсутствия вреда, а не замер доли
успешных A-BFT: такого счётчика в журнале ucode нет.

### `abft_length` на длину окна не влияет [железо]

Конфигурация BI (0x801438, данные ucode): `abft_length` = +0x0a, на железе **1**;
`fss` = +0x07 = 0x0f; `n_bis_abft` = +0x04 = 4. Слово для записи —
host **0x941440** = `{bi_at_ratio, txss_span, abft_length, addr[0]}`, на железе
0x00010100.

По стандарту A-BFT Length — число слотов SSW в A-BFT; при одном слоте случайный
выбор слота физически не работает. Запись `abft_length = 7` на оба узла (больше
в трёхбитное поле BI Control не помещается), затем возврат 1; серии по 8 снимков
`bti_duration`:

| | abft_length = 7 | abft_length = 1 |
|---|---|---|
| узел узел A | 1365, **89219**, **89212**, 1365, 1364, 1367 | 1367, **89109**, 1366, 1366, **89089**, 1366, 1365, **89076** |
| узел узел B | 1949, **17084**, **17093**, 0, 1364, 1953 | 0, **17199**, 1364, 0, **17214**, 1366, 0, **17235** |

Картина до и после записи одинакова на обоих узлах. Темп ответов SSW тоже не
меняется (+30 за 12 с в обоих состояниях), он задаётся `n_bis_abft`.

### Асимметрия длинного интервала между узлами [железо]

У двух узлов с побайтово одинаковой конфигурацией BI (`0x94143c = 0x0f000004`,
`0x941440 = 0x00010100`) длительность «длинного» интервала устойчиво различается
**в пять раз**: узел A ≈ **88.8–89.2 мс**, узел B ≈ **17.1–17.2 мс**. Длинный интервал
встречается примерно с частотой A-BFT (каждый 4-й BI при `n_bis_abft = 4`).

Прошивка сама логирует согласованный набор:

    MAC_MON [BTI] duration 88860 | [AW ] duration 1003 | [DTI] duration 12535
    (сумма 102398 ≈ 102400 = 100 TU)

То есть у узла A в таких интервалах на данные остаётся 12.5 мс из 102.

Исключены (каждая — отдельной записью с возвратом): `abft_length`, `CC Present` в
маяке (0x905a3c), `special_flags` (0x903474). После отката всех трёх на узле A
асимметрия сохраняется.

### Метод

* Базу и результат рычага снимать **на одном узле** и серией, а не одиночным
  снимком; сравнение значений разных узлов (например, 16512 на узле B и 89673 на узле A)
  ложно показывает «рост окна A-BFT с 14.6 до 88.3 мс».
* `bti_duration`, читаемый выборкой из `blob_fw_peri`, иногда равен **0**: структура
  двухбуферная (`memcpy` 0x7c байт в `bi_window_transition_prep`), снимок ловит её на
  ходу. Согласованные значения брать из лога прошивки (строки
  `MAC_MON [BTI]/[AW ]/[DTI]`).

## BRP — Beam Refinement Protocol

Кадры BRP — **Action No Ack** категории **Unprotected DMG**, её номер
**20 = 0x14**; это значение байта `0x804028`. В поле BRP Request есть **L-RX** —
сколько TRN-R подполей запрошено; это бит 10 маски и байт `0x80402b`. Биты 9/10/11
маски = BRP / запрос RX-тренировки / второй запрос. Подробно — [BF-ENGINE.md](BF-ENGINE.md).

## ATI и механизм ATIM

### Прошивка никогда не объявляет ATI в маяке [код]

Бит `AT_preset` (бит 6 октета 0 поля Beacon Interval Control) зануляется в
**двух независимых местах**:

    bcn_tx_init_bi_cfg @0x8c3c98:  bi_at_ratio := 0  (0x8c3cc8/0x8c3cca)
      -> bi_cfg__fill_slot_desc @0x92821a:  next_at = 0xf  (так как ratio == 0)
      -> bi_cfg__tick_counters  @0x932ec8:  if (bi_at_ratio == 0) return;
                                            // next_at навсегда 0xf
      -> bi_ctrl__program_mac_bcon @0x93328c: r2 = (next_at == 0) << 6;
                                            // AT_preset == 0
    bcon_tx_build_step @0x8c42fc:  bclr_s r0,r0,0x6   // тот же бит в теле маяка

Узел открывает ATI **локально** (автомат BI, состояние AW) и передаёт туда
unicast-ATIM. Партнёр получает маяк с `AT_preset = 0`, своего ATI не открывает и
квитировать не обязан — кадры уходят, ACK не приходит. Так объясняется наблюдение
`tx atim pass 0 | tx atim fail 3` в логе.

### Три класса отказа ATIM

| класс | где | условие | признак |
|---|---|---|---|
| A | 0x921a68 | остаток окна `[0x88c120] & 0xffffff` меньше 0x1ef0 (unicast, 7920 тактов = **48 мкс**) или 0x13fb (bcast, 5115 = **31 мкс**) | ни один счётчик не растёт |
| B | 0x932768/6c | поднят `busy2_event` (r42) либо снят `cca_ppdu_comp` (r40) | **uc 0x800431++** (host 0x940431) |
| C | 0x921a9e | кадр ушёл, но `imm_ack` (r36) не пришёл — только unicast | **`aw_tx_atim_counter`++** (uc 0x80091b → peri 0x854e1b) |

`aw_tx_atim_counter` инкрементируется ровно в одном месте, @0x93280e, **после** гейта
CCA и **после** выдачи кадра. Значит `counter = 3` при `pass = 0` — класс **C**: три
кадра ушли, ни одного ACK.

Разница порогов 48 − 31 = **17 мкс** — SIFS+ACK; независимо подтверждается
MAC-командой 0x15 (Duration/ID): `0x15000026` = 38 мкс для unicast против
`0x15000015` = 21 мкс для bcast. MAC-команда 0x34 с `0x160018` задаёт длину кадра
**0x18 = 24 байта** — голый MAC-заголовок без тела, то есть ATIM
(см. [MAC-COMMANDS.md](MAC-COMMANDS.md)).

Подтип строится арифметикой: `asl r33,r1,0x4` при r1 = 9 даёт FC октет 0
= **0x90 = Management / subtype 9 = ATIM**. Таблицы «индекс типа → подтип» в
прошивке нет.

### Гейт окна AW — `bi_ap_mon_if__trigger_bhi` @0x930564

    930568 ld.as r1,[gp,-0xd0]   ; uc 0x800458
    930572 breq  r1,0  -> DTI    ; ГЕЙТ A: == 0 -> AW НЕТ
    930574 ld_s  r0,[gp,-0x8c]   ; uc 0x80049c
    930576 brne  r0,0  -> DTI    ; ГЕЙТ B: != 0 -> AW НЕТ
    930578 ld    r3,[0x801438]
    930580 breq  r3,0x2 -> DTI   ; ГЕЙТ C: bi_mode == 2 (DISCOVERY) -> AW НЕТ
    93058c basic_sm(0x801de8, event 3 BHI_TO_AW)

Гейты A и B в ucode никем не пишутся — это хостовые ручки (host 0x940458 должен быть
≠0, в образе 1; host 0x94049c должен быть 0). Гейт C: discovery_mode сам снимает AW,
и **рандомизатор задержки маяка (`bi_mode == 2`) и окно AW взаимоисключающи**. Роли
PCP/STA в гейте нет.

### Путь длительности AW

    power_mngr__recalc_aw @0x8dd500: r15 = 0x3e8 = 1000 (КОНСТАНТА)
      -> mid__set_awake_window @0x8e1590: stw -> mid+0x52 (fw 0x80598a)
      -> LMAC cmd 0x25 {0x9d, tbtt, dur, valid}
      -> aw_ie__copy_to_bcon @0x930420 (по назначению power_mngr__set_pend_aw:
         в шаблон маяка не пишет, только в g_power_manager.m_pend_aw)
      -> aw__set_tbtt_offset @0x930488: m_aw_duration_usec (uc 0x801ec8) = 1000,
         m_aw_duration_clks_165 (uc 0x801ec4) = 1000*165 = 165000 = 0x28488
      -> MAC-команды 0x68 (выбор группы GP) и 0x67 (24-битное значение)

Значение 0x028488 зафиксировано на железе как единственный наблюдавшийся параметр
команды 0x67 (`4.1/ref/MAC-CMD-MAP.txt`) — полное совпадение с расчётом. Элемент AW
в маяк кладёт **прошивка** (`ie__push_awake_window` @0x8ef82c), а не ucode.

### Рычаги с хоста для двустороннего ATI [гипотеза, не применялись]

Минимум, на **обоих** узлах: `bi_at_ratio` host **0x941440** байт 0 = 1
(ATI каждый BI), `next_at` host **0x941431** = 0, и бит 6 в fw **0x905a3f**
(переписывается при пересборке маяка; постоянный вариант — патч
`bclr_s`→`bset_s` @0x8c42fc, тот же размер).

Требование ACK обходится **broadcast**-классом: биты в host 0x941eb9 (байт 1
pending-вектора `m_atim_tx_pending_sta_vector`); bcast не квитируется никогда.

### Разрыв связи по неудачным ATIM [код]

«11 подряд» (`bi_window_transition_prep` @0x9370e6..0x93713e, порог
`brlt r2,0xb`; вендорская строка говорит «10», верно значение кода) выставляет бит
пира в `aw_consecutive_bcons_atim_fail_vec` (uc 0x80091d, липкий), далее
peri 0x854e1d → `conn_mgr__foreach_on_boot_done` @0x8cb4ee → fw 0x857268 →
`tx_ppdu_ageing_timeout_detector__task` @0x8e413a → лог
`tx_ageing_detector: Link-Loss detected for cid=%d. missing ack for ATIM in 10
consecutive beacons.` → `conn__disconnect`.

**Детектор вооружён только при `fw 0x803468 == 0`**, то есть вне режима OOB.
Следствие: `oob_mode=1` даёт элемент AW в маяке **и** выключает детектор;
`oob_mode=0` + PS off — элемента AW нет, но детектор вооружён.

### Счётчики ATIM и соседние переменные

* Счётчики ATIM — байты uc 0x800919..0x80091c и битмапы `m_atim_*` в
  `g_power_manager+0x134..+0x140`.
* `0x857038` / `0x85703c` — не счётчики ATIM: ни читателей, ни писателей нет ни в
  одном сегменте.
* `uc 0x8015f0..0x8015f4` — отладочные QoS-Null / traffic-suspend
  (`g_dbg_qos_null_cnt`, `_eosp_set_cnt`, `_eosp_unset_cnt`,
  `unicast_traffic_suspend_cnt`, `broadcast_traffic_suspend_cnt`); порядок совпадает
  с паком 11ad (0xa7c590) **[пак]**.
* `uc 0x8009e8` = `g_ucode_pm_db.is_pcp` (LMAC cmd 0x1b, `body[0]` =
  `mid__state_is_2_or_3`). На PCP = 1, поэтому keep-alive подмешивается в
  unicast-класс ATIM.
* `uc 0x802014` = `m_aw_occurred`.

## PCP/AP Clustering

### Стандарт

802.11ad определяет **PCP/AP clustering**: несколько точек на одном канале делят
время, каждая ставит свой маяк в отдельный **Beacon SP** внутри общего интервала.
В маяке для этого есть поле **Clustering Control** (роль члена кластера, Cluster ID,
индекс Beacon SP). Две разновидности:

* **централизованная** — ведущая точка (S-PCP/S-AP) распределяет слоты;
* **децентрализованная** — член сам выбирает свободный слот, слушая эфир.

Поддержка объявляется битом **Decentralized PCP/AP Clustering** в поле
*DMG AP or PCP Capability Information*. Прошивка гасит этот бит безусловно —
`bic r0,r0,0x38` @0x8e1882 (вместе с Power Source и PCP Forwarding); на железе
поле = 0x0000. Флаг «умею децентрализованно делить эфир с другими точками» в эфир
не выставляется никогда **[код, железо]**.

Механизмы, нужные для децентрализованного дележа, в прошивке есть по отдельности:
**рандомизатор задержки маяка** (гейт `bi_mode == BI_TX_DISCOVERY_BCON`, то есть 2;
открывается записью `0x941438 = 2`) и **NAV-отсрочка маяка**. Их описывает патент
**US8520648B2** (Intel/Cordeiro), совпадающий с кодом 1:1.

### Вендорские имена [пак]

Пак 11ad, `globals/*/ucode_image_globals.xml`, структура `bcon_interval_ctrl_ei`
(48 бит = 6 октетов, ровно поле **Beacon Interval Control** стандарта):

    CC_present     бит 0        discovery_mode бит 1
    next_bcon      биты 2..5    AT_preset      бит 6
    A_BFT_length   биты 7..9    FSS ...

`cc_present` (бит 0 поля flags конфигурации BI) — это **B0 «CC Present»** стандарта:
«в маяке присутствует поле Clustering Control». В `fw_image_globals.xml` структура
`parsed_info_elements` содержит член **`clustering_ctrl`** сразу за
`bcon_interval_ctrl` (порядок: `sector_sweep, dband_interval, bcon_interval_ctrl,
clustering_ctrl, listen_interval`) — это соответствует раскладке разбора в 4.1.

### Clustering Control в 4.1

**Передача** — `tx_mgmt_build_step` @0x8ec8de **[код]**:

    8ec8de ldb_s r0,[r14,0x17]        ; октет 0 BI Control в собираемом кадре
    8ec8e4 bbit0 r0,0x0,0x8ec8f6      ; CC Present == 0 -> пропустить
    8ec8ea bl    0x8e894c             ; вклеить Clustering Control
    8ec8f0 add_s r13,r13,r0           ; длина кадра += возврат (8)

`mgmt_tx__push_clustering_control` @0x8e894c копирует **6 байт и возвращает 8** (два
последних октета не инициализируются). Источник шести байт — **хостовый**:
`[mid+0x23c]` → `mid_ctx__at(mid_id)` = 0x805d08 + mid_id*0x90, поле `+0x64` =
0x805d6c, куда `scan_mngr__start_scan` @0x8f155c кладёт **`direct_scan_mac_addr[6]`**
из тела `WMI_START_SCAN_CMDID`. Соседняя `mgmt_tx__push_bi_control` @0x8e8960 копирует
6 октетов BI Control.

**Приём** — `rx_mgmt_prs__parse_dmg_bcon_fixed` @0x8da1f0 (разборщик фиксированных
полей DMG-маяка), участок @0x8da25e **[код]**:

    8da25e ld_s  r15,[r14,0x40]       ; указатель на BI Control
    8da260 ldb_s r15,[r15]            ; октет 0
    8da266 bbit0 r15,0x0,0x8da27a     ; CC Present == 0 -> мимо
    8da26a st_s  r1,[r14,0x44]        ; ei+0xc4 = &Clustering Control
    8da26e sub_s r13,r13,0x8          ; остаток -= 8
    8da276 add_s r1,0x8               ; съедено += 8  -> курсор IE сдвигается

Длина учтена правильно, IE после поля разбираются корректно. Смещения TX и RX
совпадают 1:1: tsf +0x00, Sector Sweep +0x08, Beacon Interval +0x0b,
**BI Control +0x0d (6 Б)**, DMG Parameters +0x13, **Clustering Control +0x14 (8 Б)**.

**Содержимое — не кластер, а адрес ответчика A-BFT.** Единственный вариант поля,
который прошивка умеет формировать, — **Discovery-вариант с A-BFT Responder
Address**, привязанный к **direct scan**. Тот же адрес идёт в `abft_responder_address`
конфигурации BI (`add_discovery_bcon` @0x8c235e).

**Принятое поле никем не читается:** у `ei+0xc4` один писатель (0x8da26a) и ноль
читателей. Из принятого BI Control читаются только бит 1 октета 0 (`discovery_mode`)
и октет 5 (`PCP_assoc_ready`).

Кто ставит и кто гасит CC Present:

| адрес | инструкция | что делает |
|---|---|---|
| **0x8c42fc/0x8c42fe** | `bclr_s r0,r0,0x6` ; `bclr r1,r0,0x0` | `bcon_tx_build_step` **безусловно гасит и AT_preset (бит 6), и CC Present (бит 0)** при сборке обычного маяка |
| **0x8c2350** | `bset_s r0,r0,0x0` | `add_discovery_bcon` ставит CC Present — **только в ветке `scan_type == 3`** |

Ветка `scan_type == 3` в стоке недостижима: у `add_discovery_bcon` @0x8c22e4 два
вызывающих, оба передают 0 в слоте задержки (`_mov_s r1,0x0` @0x8c2298 и @0x8f0dee),
ссылок из данных нет. `bcon_kind = 3` и CC Present в штатной прошивке не достигаются,
поле в эфире всегда отсутствует.

### Включение поля с хоста [железо]

`bss_bi_ctrl` = `bss+0x107` = **0x805a3f**, host **0x905a3f**. На железе октет 0
= 0x80 (CC Present 0, A-BFT Length 1). Запись слова `0x905a3c = 0x81000000`
ставит бит 0.

Стенд: узел A — PCP с CC Present = 1, узел B — приёмник.

* **Бит держится** — три проверки за 12 с, значение 0x81000000 не сбрасывается:
  `tx_bcon__update_bcon` вызывается по событиям, а не на каждый маяк.
* **Партнёр разбирает удлинённый маяк без сбоев**, окно 12 с: чужих маяков
  **+5599** (тот же темп, что до записи), `handled_ppdus` +8378, ложных
  срабатываний +77, отправлено SSW +30 (2.5/с — ровно `n_bis_abft = 4`), связь жива.

Поле Clustering Control уходит в эфир и корректно разбирается обеими сторонами без
патча прошивки. Узел умеет поставить флаг, вклеить 8 октетов и разобрать их на
приёме — готовая эфирная основа для собственного содержимого поля.

### Чего нет

Non-Discovery вариант поля: **Cluster ID, Cluster Member Role (non-member / cluster
member / S-PCP-S-AP), Beacon SP Index, число членов** — ни полей, ни констант, ни
строк, ни структур. Нет состояния членства, выбора свободного Beacon SP, слежения за
занятыми слотами. Централизованной кластеризации следов нет.

Слов `cluster`, `Cluster ID`, `beacon SP`, `S-PCP` нет ни в одном блобе строк 4.1.
В паке 11ad единственное имя — `clustering_ctrl`, тот же 32-битный слот в разобранном
маяке; структур состояния кластера нет и там. Отличие wil6436 (по паку): принятое BI
Control хранится в ucode, и есть поля `my_bti`, `abft_allocated`, `BSS_IBSS_MODE` в
`g_bhi_db.bti_db` — заготовки под «мой слот в общем интервале», которых в 4.1 нет.

К Beacon SP **не относятся** `bi_manager__eval_bcon_slot` @0x9262e0 и
`beacon_tx__build_slot_bitmap` @0x932e00 — это битовая карта 64 **секторов развёртки
TXSS**. `bcon bitmap` в MAC_MON мертва по коду (писателя нет).

Итог: механизма дележа интервала между точками в 4.1 нет — Clustering Control здесь
лишь переносчик 6-байтового адреса. Штатные механизмы дележа эфира — рандомизатор
задержки маяка (`bi_mode == 2`, запись `0x941438 = 2`) и NAV-отсрочка.

## OCB (802.11p) и DMG

OCB = «outside the context of a BSS»: `dot11OCBActivated`, кадры с широковещательным
BSSID, ни ассоциации, ни аутентификации, маяки не нужны. **В DMG такого режима нет.**
Ответ 802.11ad на одноранговость — **PBSS** (есть PCP, но станции обмениваются кадрами
напрямую) плюс **PCP handover** плюс кластеризация.

Режим OOB похож на OCB по наблюдаемому поведению (ответ в A-BFT независимо от
ассоциации, снятые детекторы разрыва, фиксированный MCS), но конструктивно другой:
ассоциацию он не отменяет — см. [ROLELESS-LINK.md](ROLELESS-LINK.md).

## Интервал маяка и потеря связи у станции

### Требования 802.11-2020 [стандарт]

* **§9.3.4.2, Table 9-45 — DMG Beacon:** тело = Timestamp (8), Sector Sweep (3),
  **Beacon Interval (2, TU, §9.4.1.3)**, Beacon Interval Control, DMG Parameters, …
  С заголовком (FC 2 + Duration 2 + BSSID 6) поле Beacon Interval лежит по смещению
  **0x15** от начала кадра.
* **§11.1.3.3.1** (DMG infrastructure BSS и PBSS): «The length of the beacon interval is
  included in the DMG Beacon, Announce, and Probe Response frames, and a DMG STA **shall
  adopt that beacon interval when joining the BSS**.» (§11.1.3.2 — то же для не-DMG сетей.)
* **§11.1.2.1 / §11.1.3.1:** в DMG-инфраструктуре AP шлёт ноль или больше DMG Beacon
  за dot11BeaconPeriod и хотя бы один через каждый свой сектор за
  dot11BeaconPeriod × dot11MaxLostBeacons; «the STAs expect to receive at least one DMG
  Beacon frame every **dot11BeaconPeriod × dot11MaxLostBeacons** TUs». Next Beacon /
  TXSS Span разрешают AP пропускать BI.
* **§9.4.2.128 DMG Operation, Figure 9-557 (DMG BSS Parameter Configuration):**
  **MaxLostBeacons** (1 октет) — значение dot11MaxLostBeacons, объявляет AP.
* **§11.1.3.7:** «An active DMG STA that is receive beamforming trained with the AP or
  PCP shall direct its receive antenna pattern toward the AP or PCP **or use a
  quasi-omni antenna pattern** during this time» — «this time» = не меньше
  dot11MinBHIDuration после TBTT (или начала ATI). Для этого окна quasi-omni прямо
  разрешён; про DTI пункт ничего не говорит.

### Поведение стоковых прошивок

| | период маяка станции | adopt по §11.1.3.3.1 |
|---|---|---|
| **[4.1]** | зашитые 100 TU (при BI точки 200 у станции 0x886d64 = 0x64) | нет |
| **[6.2]** MikroTik | глобал fw 0x8002d4 из WMI 0x803 (эхо), берётся в `l2_mgr__connect` при `WMI_CONNECT` — до приёма маяка; мейнлайн шлёт 0x12345678 → 0x5678 | нет |

Детектор `bad_beacons` прошивки: порог `bad_beacons_num_threshold` (20) BI подряд без
маяка — аналог dot11MaxLostBeacons, но из собственной конфигурации, а не из DMG
Operation AP.

### Исправление по стандарту

Драйвер перед `WMI_CONNECT` посылает 0x803 с `beacon_interval` выбранной BSS
(cfg80211 берёт его из Beacon/Probe Response) — прошивка программирует период станции
равным периоду AP в момент присоединения; при старте — 100 (align 0) вместо
0x12345678. Реализация и проверка на железе для 6.2 — [6.2/docs/BENCH.md](../6.2/docs/BENCH.md).
Порог потери из MaxLostBeacons AP — там же.

## Энергосбережение без графика (11.2.7.2.2, DMG-M13.1)

### Требования 802.11-2020 [стандарт]

Обязательный для DMG STA режим (PICS DMG-M13.1, CFDMG:M) — PS без графика
(unscheduled PS). Режим с графиком (PSC-REQ/RSP, Wakeup Schedule, 11.2.7.2.3) —
необязательный.

* Станция меняет состояние только успешным обменом, который начала сама: кадр с
  битом Power Management в FC и Ack/BlockAck от AP.
* Пока хоть одна станция спит, AP обязан объявлять Awake Window и включать
  элемент UPSIM (9.4.2.166, EID 200) в каждый DMG Beacon и Announce. UPSIM — карта
  спящих по AID (256 бит; передаются октеты N1..N2), флаг PS Non-PCP = спят все.
* Каждый BI для спящей станции — A-BI; нисходящие данные объявляются ATIM в AW
  (11.2.7.4), получившая ATIM станция выходит из doze.

### Что есть в стоковых прошивках [код]

* 4.1 — режима нет: бит PM не ставится и не читается, есть только PSC и ATIM.
* 6.2 — почти есть (вендорское имя UPM). Станция: вход и выход обменом с Ack
  (`internal_tx__flow_sm6`), флаг doze в объекте PM ucode 0x802f80+0x179. AP:
  бит PM принятых кадров (R38 бит 26) копится в `upm_vector` 0x802f80+0x178, fw по
  событию 0x16 гасит кольца спящих. Нет: UPSIM; AW зависит от профиля PS точки, а
  не от спящих; вход в doze только при договоре PSC; таймер простоя GP8 первый раз
  не взводится; маска «сплю» станции уходит в fw флагом 0/1; команду включения
  (WMI 0x960) драйвер не шлёт.

### Прошивка 6.4 apsta [код; железо — не проверено]

| что | блок |
|---|---|
| UPSIM в DMG Beacon, AW при спящих | `tx_mgmt_build_step` (C), `new/ps_upsim.cpp` |
| пересборка маяка при смене маски спящих | `conn_mgr__start_all_detector_services` (C) |
| вход в doze без договора PSC | `ps__hold_awake_if_active` (C, ucode) |
| взвод таймера простоя при включении | `ucode_cmd_0x33_handler` (C, ucode) |
| маска спящих у станции — все CID | `tx_ctx__post_status` (C, ucode) |
| UPM выключен при старте (в 6.2 был включён) | патч 0006 |
| выключение хостом переживает скан | `ucode_cmd_0x33_handler` (C) |
| UPM по профилю PS хоста (MLME-POWERMGT, `iw set power_save`), только станция с открытым портом | `new/upm.cpp`, `ps_connection_mgr__on_assoc`, `m_connect_devid` (on_disassoc), `POWER_MNGR__wmi_ps_dev_profile_cfg_cmd` (C) |
| выход из doze при отключении | `ps__release_awake_for_sta` (C, ucode) |
| выход из doze по ATIM и по своим данным — в начале DTI | патч 0007, `new/upm_wake.cpp`, `bi__dti_step` (C, ucode) |
| ATIM точки станциям, уснувшим по PM | патч 0012, `upm__collect_awake_peers` |

На стенде (2026-09-29, apsta, пара AP↔STA) **[железо]**: после `iw set power_save on`
и 5 с простоя станция в doze (ucode `upm_enable` = 1, `in_doze` = 1), точка видит бит PM
(`upm_vector` = 1) и пересобирает маяк с UPSIM («PS: sleeping CIDs 0x0 -> 0x1, DMG
Beacon rebuilt with UPSIM»); восходящий трафик будит станцию (пинг без потерь, до 1 BI
задержки), iperf3 вверх при PS — 979 Мбит/с; `power_save off` всё снимает; разрывов и
ошибок fw нет. Нисходящий трафик к спящей станции: сначала ATIM точка не передавала
(MAC_MON «tx atim counter 0») — цели ATIM собирает `aw_worker__collect_awake_peers`, станции
в UPM без PSC туда не попадали; патч 0012 (`upm__collect_awake_peers`) добавляет спящих с
данными. С ним нисходящий пинг к спящей станции — без потерь, задержка до 1 BI (первый кадр
~1 с). Doze логический: DMA кольца точки не останавливается (head догоняет tail), регистр
0x881c84 чаще пуст, и станция с включённым радио принимает кадры, затем просыпается по
ответу **[железо]**.

Doze логический — радио не выключается; неглубокий сон 4.1 — отдельная задача
ради экономии. Не сделано: UPSIM в Announce (fw Announce не передаёт вовсе);
момент обмена-выхода относительно AW чужой точки без своего AW не установлен.

## Замечания

* Имя `aw_ie__copy_to_bcon` (ucode @0x930420) ложное: в шаблон маяка функция не
  пишет, только в `g_power_manager.m_pend_aw`; по назначению — `power_mngr__set_pend_aw`.
* Синонимы имён (прежние авто-имена в выгрузках): 0x8e8960 `mgmt_tx__copy_addr_from_mid` =
  `mgmt_tx__push_bi_control`; 0x8e894c `mgmt_tx__copy_addr_from_conn` =
  `mgmt_tx__push_clustering_control`; 0x8da1f0 `rx_mgmt_prs_step` =
  `rx_mgmt_prs__parse_dmg_bcon_fixed`.
* `l2_mgr__scan_start_log` @0x8f0134 — переходник к `scan_mngr__start_scan`;
  `l2mgr__mac_started_log` @0x8f141c — обёртка над `bcon_tx_build_step`.

## Не установлено

1. Что растягивает окно A-BFT у одного PCP в пять раз против другого при одинаковой
   конфигурации BI.
2. Точное соответствие `n_bis_abft` имени поля стандарта; природа `relaxation_period`.
3. Работоспособность двустороннего ATI при включении рычагов с хоста.
