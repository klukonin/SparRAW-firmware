# Патч постоянного распределённого биконинга

Однобайтовая правка, при которой рандомизированная отсрочка маяка
([../../docs/BEACONING.md §4](../../docs/BEACONING.md#4-рандомизатор-отсрочки-маяка-обе)) применяется
к обычному маяку PCP, а не только к discovery-маякам активного скана. Готовые образы — в
`images/sparraw/experimental/`. Без патча тот же гейт открывается записью с хоста `0x941438 = 2`
([../../docs/BEACONING.md §9.1](../../docs/BEACONING.md#91-открытие-гейта-с-хоста-41-железо)).

## Назначение

Рандомизатор (`bti_worker__bti_transmitter_beacon_sweep_flow` 0x923de0,
`uniform=((rnd*0xbd)>>32)+10`) гейтится условием `bcon_kind == 2`, а `bcon_kind = 2` ставит только
`add_discovery_bcon()` — на время активного скана. Штатный маяк PCP идёт с `bcon_kind == 1`
([../../docs/BEACONING.md §2.2](../../docs/BEACONING.md#22-кто-ставит-bi_mode-обе-код)).
Патч разрывает эту привязку.

Из читателей `bcon_kind` (таблица в [BEACON-CONFIG.md §3](BEACON-CONFIG.md#читатели-блока-в-ucode))
побочный эффект смены значения 1→2 даёт гейт окна AW в `bi_ap_mon_if__trigger_bhi` (@0x930578;
событие автомата `0x801de8`: 2 вместо 3); у правки самого гейта побочных читателей нет.

## Вариант A — гейт в ucode (используется в образах) **[обе]**

```
bti_worker__bti_transmitter_beacon_sweep_flow (0x923de0):
  mov r13,0x801438
  ld  r7,[r13]
  cmp r7,0x2          ->  cmp r7,0x1
  bne.d <выход>
```

Кодирование: в 32-битной ALU-инструкции ARC u6-иммедиат лежит в битах **[11:6]** младшего
полуслова: `4c 27 80 80` (u6=2) → `4c 27 40 80` (u6=1).

| прошивка | рандомизатор | гейт | байт (AHB) | было→стало |
|---|---|---|---|---|
| **4.1.0.1000** | `0x923de0` | `0x923e0c cmp r7,0x2` | **0x923e0e** | `80` → `40` |
| **6.2.0.1000** | `0x923cb4` | `0x923cda cmp r9,0x2` | **0x923cdc** | `80` → `40` |
| **5.2.0.18** (linux-firmware) | `0x92377c` | `0x9237a0 brne.d r2,0x2` | **0x9237a2** | `b1` → `71` |

В 5.2 гейт — одна инструкция `brne.d r2,0x2,<выход>`; u6 в тех же битах [11:6], цель перехода
(0x923840) не меняется. Все три правки проверены дизассемблером **[код]** (setBytes в Ghidra
`-readOnly` → `cmp rX,0x1` / `brne.d r2,0x1,0x00923840`); для 5.2 используется отдельный
Ghidra-проект (`kit-52`).

Побочный эффект: discovery-маяки активного скана перестают рандомизироваться (гейт теперь на 1).
Чтобы рандомизировать оба вида — заменить `cmp`+`bne` на «kind != 0» (`breq r7,0,<выход>`, 4 байта).

## Вариант B — константа в fw (образов нет)

`tx_bcon__update_bcon` @0x8c224a: `mov_s r1,0x1` (`01 d9`) → `mov_s r1,0x2` (`02 d9`) — обычный
маяк объявляется discovery-маяком целиком. Проверено дизассемблером **[код]**. В 6.2 та же
константа кодируется `01 d8` → `02 d8`. ucode не затрагивается, но срабатывает побочный эффект
гейта AW (0x930578) и меняется поведение всего, что смотрит на `bcon_kind`.
Константа лежит в общей точке слияния ветвей, поэтому правка действует и при bss_mode==2, и для
обычного AP; сделать её условной «только bss_mode==2» одним байтом нельзя — нужна перестановка
двух инструкций.

## Образы

| файл | размер | основа | отличие |
|---|---|---|---|
| `images/sparraw/experimental/wil6210_4.1.0.1000_distbcn.fw` | 347520 Б | `images/openwrt/fw/wil6210_4.1.0.1000.fw` | 5 байт: 4 байта CRC заголовка + код @file-off `0x3e242`; CRC 0x9b9f862a |
| `images/sparraw/experimental/wil6210_5.2.0.18_distbcn.fw` | 400364 Б | `images/vendor/fw/wil6210_5.2.0.18.fw` (linux-firmware, `wil6210_mainline.fw`) | 5 байт: 4 CRC + код @file-off `0x46ee2`; crc 0x7baa5386 |

### Исходный образ 4.1 для OpenWrt

`images/openwrt/fw/wil6210_4.1.0.1000.fw` — немодифицированный код, только приведение формата:

* 476552 → **347520 Б**, records 12 → 10, типы `[6,2,2,2,2,7,2,2,2,1]`;
* crc **0x4498952f** (совпадает с вендорским заголовочным);
* comment `FW version: 4.1.0.1000`;
* loadable-адреса: 0x8c0000, 0x900000, 0x920000, 0x940000, 0x88a208/608/004;
* sha256 `6adc58666a11549beb7733d19819fd4db3ce9843d283f37d04f689df8d8c83c4`.

Образ 5.2 уже в mainline-формате (15 записей, все типы известны), strip не нужен. На нём PBSS
поднимается на ванильном драйвере **[железо]**. В 5.2 нет строковых таблиц и телеметрии —
наблюдение только зондом TSF. 4.1 — единственная инструментованная версия (счётчики @0x854de0 и лог
`uniform_random`).

## Сборка

```sh
# 4.1
SRC=images/vendor/fw/wil6210_4.1.0.1000.fw
python3 SparRAW-tools/re/wil_syms.py patch $SRC --addr 0x923e0e --bytes 40 -o step1.fw
python3 SparRAW-tools/re/fw_strip_for_openwrt.py step1.fw -o wil6210_4.1.0.1000_distbcn.fw
# исходный OpenWrt-образ без правки:
python3 SparRAW-tools/re/fw_strip_for_openwrt.py $SRC -o wil6210_4.1.0.1000_openwrt.fw
# 5.2 (strip не нужен)
python3 SparRAW-tools/re/wil_syms.py patch images/vendor/fw/wil6210_5.2.0.18.fw \
        --addr 0x9237a2 --bytes 71 -o wil6210_5.2.0.18_distbcn.fw
```

Проверка 4.1:

* diff с `wil6210_4.1.0.1000_openwrt.fw` — ровно 5 байт (CRC + `0x3e242`);
* байты по AHB 0x923e0c: `4c 27 40 80` против эталонных `4c 27 80 80`;
* все 7 сегментов на месте, размер совпадает, CRC пересчитан (0x9b9f862a).

## Проверка на железе

### Результат **[железо]**

Узел в режиме AP без партнёра, `wil6210_4.1.0.1000_openwrt.fw` (md5 514ad929) против
`wil6210_4.1.0.1000_distbcn.fw` (md5 8293df9d), снимки кольца `blob_uc_data`:

| показатель | сток (900 снимков, 30 мин) | патч (197 снимков, 7 мин) |
|---|---|---|
| снимков со строкой `randomize beacon` | **0 из 900** | **197 из 197** |
| значений `uniform_random` | нет | 2956; диапазон **10 … 198**, среднее **104,2** (теоретическое (10+198)/2 = 104) |
| интервал TBTT, непрерывный поток | 102 400 мкс | 102 400 мкс (медиана и среднее), σ = 414 мкс; 5942 интервала, все ×1 |

Типичный цикл на патче:

```
L1_TASK PRE TBTT
bti_worker::bti_transmitter_beacon_sweep_flow() randomize beacon
set_tsf_event()
bti_worker::...() current_tsf: 0x0380dffd, Next tsf: 0x03b56800, uniform_random: 135
BI_AP_MONITOR_SM: AW EVENT
BI_AP_MONITOR_SM: DTI EVENT
```

Правка включает расчёт на каждом интервале маяка, но маяк во времени не сдвигается: длительности
BTI/AW и шаг начала BTI у стока и патча неразличимы, у станции, связанной с пропатченной AP,
интервал тот же. Причины (путь передачи не ждёт компаратора TSF, накопитель цели не привязан к
TSF) — [../../docs/BEACONING.md §9.2](../../docs/BEACONING.md#92-рандомизатор-маяк-не-сдвигает-41-железо--код).
Поведение двух узлов с пропатченным образом не проверялось.

### Метод

1. Загрузить `wil6210_5.2.0.18_distbcn.fw` (замена файла linux-firmware) либо, для диагностики,
   `wil6210_4.1.0.1000_distbcn.fw`; поднять PBSS. Иметь снимок стоковой прошивки для отката.
2. `SparRAW-tools/host/wil_tsf_probe.py` без скана: `NextTSF − TSF` меняется от прохода к проходу
   (на стоке — постоянно); смысл и ограничения цели компаратора —
   [../../docs/BEACONING.md §9.2](../../docs/BEACONING.md#92-рандомизатор-маяк-не-сдвигает-41-железо--код).
3. `SparRAW-tools/host/wil_ucode_log.py` — строка `bti_worker::…uniform_random: %d` со значением
   в [10,198] на каждом маяке (только 4.1). Снимать непрерывным потоком
   (`SparRAW-tools/host/wil_uc_stream.py`): кольцо ~126 записей (~1,5 с), выборочные снимки раз в 2 с
   дают ложные «пропуски» маяка кратно BI.
4. `SparRAW-tools/host/wil_beacon_stats.sh` — счётчики `tx bcon`/`rx bcon`/`detected`.
5. PBSS-AP на обоих узлах, `bcon bitmap` у обоих.

## Замечания

* Если бы рандомизация сдвигала штатный маяк PCP относительно TBTT, связанная STA могла бы терять
  маяки; на железе сдвига нет (см. «Результат»).
* `bad_beacons_detector` (пороги `bad_bcons_cnt`, `bad_beacons_num_threshold`) может считать такие
  маяки «плохими».
* Вариант A не затрагивает NAV-отсрочку.

## Не установлено

* Поведение двух узлов с пропатченным образом; поведение образа 5.2 на железе.
