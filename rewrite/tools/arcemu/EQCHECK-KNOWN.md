# Известные расхождения eqcheck

Функции, которые `eqcheck.py` (случайные сиды, `--seeds 30..40`) помечает `diff`, хотя
поведение в штатной работе совпадает с vendor 6.2 — или причина пока не разобрана.
При регрессионной сверке их «diff» ожидаем; новое расхождение в другой функции — повод
разбираться.

Полный прогон `--all --seeds 30` (2026-10-17, 801 функция, ~4 ч на 10 процессах; выдача идёт по
порядку, медленные функции вроде `l1_fixed_sched_ap_sm` задерживают её): все `diff` перечислены
ниже. Множитель `xN` — отношение числа инструкций наш/vendor без вызываемых; у vendor-функций,
которые хвостом уходят в общий помощник (`brp_set_tx_sector_id`, `bits_set_*`), он завышен.

## Причина установлена — артефакт проверки

| Функция | Что расходится | Почему это не отличие |
|---|---|---|
| `brp_rf_store_cfg` | RAM 0x80150c | случайный `c` огромный, цикл читает стек; с реальными `c` (0..32) — equal |
| `bti_arm_period_gp0` | число событий (10 / 4) | при случайных r55 цикл вычитания периода — до 10⁶ итераций, наш цикл длиннее (3 инструкции у vendor) и не укладывается в лимит шагов; в штатной работе итераций единицы |
| `ucode_cmd_0x0c_handler` | 2 байта кольца журнала | assert при индексе ≥ 9 пишет в журнал адрес возврата — у нас другие адреса кода |
| `tx_ctx_post_status` | байты тела события | случайный невыровненный `r0`; компилятор слил две байтовые записи в одну `sth`; с `r0 = 0x802f80` — equal |
| `tx_bcast_flow` | слово MAC-очереди | vendor кладёт в дескриптор мусор со стека, у нас 0 (`macq_desc`) |
| `sched_bitmap_prev/next_set_bit` | порядок чтения половин `mcs_en_vec` | обычная память DCCM, порядок не наблюдаем |

## Исправлено после разбора

* `txss_order_known_sectors_first` — после assert 0x5d (сектор ≥ 0x40) vendor отмечает
  сектор во второй маске, у нас была первая (b0d39da9).
* `txss_init_send_ssw_fdbk` — vendor пишет только buf[0..1] кадра SSW-Feedback (`stw r3,[sp]`),
  Duration (buf[2..3]) уходит мусором стека; у нас 0, как в кадрах из шаблонов DCCM.
  eqcheck: `diff` в первом слове FIFO, младшая половина совпадает.
* `brp_read_rf_id` — возвращала маску; vendor возвращает r0 последнего вызова, вызывающие
  возврат не используют — теперь `void` (2282ed6d).
* `direct_tx_build_desc` (0x92bf38) — тот же кадр SSW-Feedback для `direct_tx_step`: vendor
  `stw 0` в d[0..1], затем ld/st всего слова с полями FC — Duration остаётся мусором стека
  вызывающего. У нас слово целиком = 0x0964 (FC), Duration 0; eqcheck: `diff` ровно в d[2..3].

## Исправлено в eqcheck

* Модель неинициализированной RAM (словарный мир): значение байта зависело от того, был ли
  до чтения записан соседний байт того же слова, и от ширины/выравнивания чтения. Ложные
  расхождения: `config_brp_rf` (наш код пишет `brp_pick.selected = 0` до чтения
  `count`/`snr_cfg`, vendor — после), `aw_set_new_tbtt` (невыровненный случайный `p`, ld против
  ldw), `fsched_run_tx_slot_twice`, `direct_tx_build_desc`. Теперь каждое задетое слово
  заполняется по (seed, адрес) только в незаписанных байтах.
