# Тесты прошивки (pytest)

Проверка нового образа перед выпуском: статически, по дереву исходников и на стенде из двух узлов.

```sh
pip install -r rewrite/tests/requirements.txt   # pytest, pytest-check (в отдельном venv, если система не даёт)
cd rewrite
python3 -m pytest tests --fw <образ.fw>                          # образ: структура, CRC, метка, строки журнала
ARC_DIR=<тулчейн> python3 -m pytest tests/test_tree.py           # дерево: сборка без предупреждений, proto.h, fwsh
python3 -m pytest tests --fw <образ.fw> --stand tests/stand.toml \
        [--ko wil6210.ko] [--peer-fw <образ>] [-m 'not slow']     # всё, включая стенд ('not long' — без 5-минутных замеров)
```

Без `--stand` стендовые тесты пропускаются, без `--fw` — проверки образа. Стенд описывает `tests/stand.toml`
(образец — `stand.example.toml`; сам файл в git не кладётся). Журналы упавших стендовых тестов (dmesg и журнал fw
обоих узлов) — в `--artifacts` (по умолчанию `test-artifacts/`).

## Что проверяется

| файл | метки | что |
|---|---|---|
| `unit/` | unit | без стенда: функции и цепочки uc в эмуляторе ARC против текста 802.11-2020 (`tests/unit/README.md`) |
| `test_image.py` | image | записи образа целые, CRC и длина заголовка, версия `X.Y.Z.B-SparRAW[-PRO]`, запись-метка проекта, сегменты данных — в известных областях без перекрытий, таблицы своих строк журнала (fw, uc) |
| `test_tree.py` | tree | чистая сборка fw.elf и uc.elf без предупреждений, `fw/proto.h` актуален, адреса общего блока fw/uc совпадают, образ из дерева проходит `test_image` |
| `test_boot.py` | stand, sta | первыми: dut и peer загружены с нужной прошивкой (md5 файла, версия из wmi_evt_ready), dut — с нужным драйвером (md5 модуля, версия SparRAW в сообщении probe), станция подключилась |
| `test_sta.py` | stand, sta | dut — станция: нет ошибок FW, ping, пропускная способность в обе стороны (пороги в `stand.toml`), нет разрывов под нагрузкой, длинные замеры `test_throughput_long_up/down` (iperf3 `[test] iperf_long_s` = 300 с, интервалы 10 с: ни одного ниже `iperf_long_min_frac` × порога, без «lost link», разрывов и ошибок FW; все интервалы — в выводе), в журнале fw нет фатальных ошибок; переподключение после перезапуска точки (известная проблема — xfail) |
| `test_ftm.py` | stand, sta, pro | только SparRAW-PRO: измерения FTM, слово +0x0e адресата не останавливает FTM, SESSION_END: PARAMS_ERROR для канала вне 0..3 (BUSY стендом не воспроизвести — сессия короче передачи команды) |
| `test_sta_robust.py` | stand, sta | неверные значения в командах хоста — отказ с записью в журнале, fw жива, связь есть |
| `test_stand_nodeboot.py` | — | без стенда: итерация на подставном узле — reboot → «драйвера нет» → прошивка в tmpfs → firmware_class.path → роль без commit → insmod → wifi up; ни rmmod, ни modprobe -r, ни wifi down/reload; снятие питания не больше одного раза; пропажа узла — reboot -f, затем драйвер командой |
| `test_ap.py` | stand, ap | dut — точка, peer — станция на том же образе: подключение, ping, пропускная способность, длинные замеры `test_throughput_long_up/down` (как в `test_sta.py`), останов точки без ошибки |

Порядок прогона задаёт `conftest.py`: станция → FTM → неверные команды → точка (смена роли — перезагрузка
узла). Тест, оборвавший связь, не портит следующие: фикстура роли проверяет связь и при необходимости
перезагружает стенд. Обе стороны — на проверяемом образе (peer — `--peer-fw`, иначе образ dut). После теста AP peer
возвращается в роль точки.

## Стенд

Два узла OpenWrt с wil6210 (Sparrow) по ssh с ключом, питание обоих — розетки Tapo
(`SparRAW-tools/host/tapo_plug.py`). Драйвер wil6210 сам после загрузки системы не грузится — однократно на каждом
узле `tools/stand/node_boot.sh --install <host>` (`docs/STAND.md`). Каждая загрузка роли — `sync; reboot -f`
(`[test] reboot`), затем командой (`tools/stand/nodeboot.py`): прошивка итерации в `/tmp/sparraw-fw`
(`firmware_class.path`, флеш не трогается), роль в uci без commit и один `ubus call network reload` (до insmod),
`insmod` модуля (`--ko` → `/tmp/sparraw-drv`, иначе модуль системы) с параметрами `[test] modparams`,
`ubus call network.wireless up` (не `wifi up`), проверки (версия fw в dmesg, прошивка стартовала один раз —
`[test] max_fw_starts`, роль поднята один раз, md5 fw/модуля/платы, интерфейс роли, связь станции без Disconnect
10 с). Смена — только новой перезагрузкой: `rmmod`, `modprobe -r`, `wifi down`/`up`/`reload` стенд к узлу не
отправит. Адреса, nft и `iperf3 -s` — командами после загрузки.

Восстановление: узел не отвечает по ssh — ожидание (мог перезагрузиться сам), затем одно снятие питания через Tapo
(не больше `[test] max_power_cycles`, по умолчанию 1, за прогон на узел; дальше — ошибка стенда без повторов). Зависла
команда, а узел отвечает — ошибка теста без снятия питания. Роль стенда при этом сбрасывается, следующий тест
поднимает её заново перезагрузкой. Число снятий питания — в сводке pytest. Пропажа партнёра в `test_*_vanish` —
`sync; reboot -f` по ssh (без скриптов остановки, Disassociation не уходит), не питание; после неё тест сам
загружает драйвер командой. Ошибки FW считаются только с начала
текущей роли (по времени ядра в dmesg): старые записи долгоживущего peer не мешают.

Мягкие проверки — [pytest-check](https://pypi.org/project/pytest-check/): тест, сверяющий несколько независимых
вещей (версии на обоих узлах, запись в журнале и отсутствие ошибки FW, up и down), берёт фикстуру `check` и
вызывает `check.is_true(cond, msg)` / `check.equal(got, want, msg)`; все несовпадения выводятся в конце теста.
