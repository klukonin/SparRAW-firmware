# TDMA DMG точки: простое деление и строгий SP (802.11-2020 10.39)

Расписание DTI точки SparRAW (open) — Extended Schedule в DMG Beacon (9.4.2.131, 10.39.6). Два режима, выбор —
`WMI_SPARRAW_TDMA_CFG` (0x0f10), по умолчанию — простое деление:

| режим (байт `mode`) | DTI | кто начинает обмен | где |
|---|---|---|---|
| 0 — простое деление (решение 2026-10-23) | общее CBAP 255→255 + CBAP «станция i → точка» поровну | станция i и точка в своём CBAP (10.39.5), все — в общем | fw/tdma.c `tdma_equal_build` |
| 1 — строгий SP (решение 2026-11-07, open: это стандарт) | общее CBAP + на станцию i SP «точка → i» и SP «i → точка» поровну (+ CBAP остатка BI) | в SP — только источник, получатель только отвечает, прочие молчат (10.39.6.2); в CBAP — 10.39.5 | fw/tdma.c `tdma_sp_build`, uc/ese_dti.c |

Включается сам при `min_sta` (по умолчанию 2) и более станциях, при меньшем — снимается (CBAP Only = 1). Расписание
хоста (WMI 0xa01) и фиксированное расписание vendor (WMI 0xa03) TDMA точки не трогает / снимает.

## 1. Что было до строгого режима

* **fw/tdma.c** (простое деление): ESE псевдостатический (B7 = 1, один блок), окна после BTI и A-BFT
  (`tdma_dti_start_us`), между окнами Tguard (10.39.6.5: A = dot11MaxLostBeacons = 4, C = 20 ppm, D = BI), Allocation
  Start — каждый BI заново, в середине BI на следующий (`tdma_arm` → `tdma_refresh_cb`, 10.39.6.4: станция
  игнорирует аллокацию с прошедшим началом). Своей таблицы окон у точки не было: точка — назначение каждого окна.
* **Станция** (fw/rx.c): по маяку своей точки — флаг «DTI расписан» (`fwsh_diag.ese_dti_sched`: ESE есть, CBAP Only
  = 0) и таблица окон `ese_slot_tbl` (3 записи, раскладка vendor): SP, где станция источник (б7 «начинать можно»)
  или назначение, и CBAP с Source = свой/255 или Destination = свой. fw закладывает записи в **аппаратный массив SP**
  (`lmac_if_evt_walk`: 0x886f84 конец, 0x88c050 начало, 0x886f88 слово; каждая 4-я — б6, подкачка по событию uc
  0x29), MAC даёт r54 б4 на началах и концах записей.
* **uc** (uc/ese_dti.c, порт 6.4): на начале DTI и событиях массива — пауза/возврат очередей пира
  (`bf_pause_sta_tx` причина 8); окно ищется по TSF (события сливаются: конец окна и начало соседнего через
  Tguard). Остаток окна — для Duration SSW/SSW-Feedback (`dti_alloc_left_us`, 9.3.1.15/16). У точки — ничего.
* **Границы окна для TXOP** — не было: TXOP, начатый в хвосте окна, уходил за его конец. План TXOP у MAC —
  `REMAINING_TIME` = min(лимит TXOP, до TBTT − 2 мкс) (MAC-STAND «NAV RTS и TBTT»); SP-конца MAC не знает (не
  установлено), лимит TXOP при открытии на текущий TXOP не действует (опыт 2026-10-31).
* **Ветка pro**: наработок строгого TDMA (SP/Poll/SPR/Grant) нет — только тот же простой TDMA; кадры Grant/Grant Ack
  в uc есть у фиксированного расписания vendor (uc/fsched.c, test_uc_grant_frame.py).

## 2. Строгий SP: устройство

### 2.1 Точка: расписание (fw/tdma.c `tdma_sp_build`)

```
TBTT | BTI | A-BFT | g | CBAP 255→255 2 мс | g | SP 0→1 w | L | SP 1→0 w | L | SP 0→2 w | … | SP n→0 w | [g | CBAP 255→255 остаток] | g | TBTT
```

* g = Tguard (10.39.6.5), L = max(Tguard, aDMGPPMinListeningTime 150 мкс) — у всех SP общая STA (точка), 10.39.6.2
  «should … separated by at least aDMGPPMinListeningTime»; w = (BI − T0 − общее − g − (2n − 1)·L − g) / 2n.
* SP: Allocation Type 0, Allocation ID 1 (кортеж различается адресами), Pseudo-static 1, **Truncatable = Extendable
  = 0** (усечение и продление — следующий этап), PCP Active 1 (10.39.6.1), BF Control 0, один блок.
* w ≤ 32 767 мкс (9.4.2.131, SP); при n = 1 и BI 100 TU SP упираются в предел — остаток BI отдаётся CBAP 255→255
  (поле ESE 17-е — при n ≤ 7). w < 1 мс — расписание снимается (как в простом делении).
* T0 считается по длине маяка с наибольшим ESE (с CBAP остатка) — окна не раньше конца BHI при любом исходе.
* Проверка — ref/schedule.check над маяком (BIC и DMG Parameters из маяка, A-BFT по BIC): нарушений нет при 1, 2, 3, 8
  станциях (tests/unit/test_tdma_strict.py).

### 2.2 Точка: своя таблица окон

`ese_own_tbl` (0x857978, 9 записей по 12 Б, тот же формат, что `ese_slot_tbl`, SparRAW): окна, где точка начинает
обмен, — общее CBAP (получатели — все, peer 0xff), SP «точка → i» (peer = 1 << cid_i), CBAP остатка. SP «i → точка» в
ней нет: там точка не начинает обмен (10.39.6.2), вне записей своей таблицы uc передачу закрывает. Признак для uc —
`ese_slot_tbl.mode = ESE_TBL_MODE_OWN` (3): vendor-fw этот режим не пишет, гибрид vendor-fw + наш uc таблицу (память за
0x857828 vendor не обнуляет) не читает. Таблицу обхода `ese_sched.tbl` fw переключает на `ese_own_tbl`; аппаратный
массив SP закладывается тем же `lmac_if_evt_walk` только при смене раскладки окон (отпечаток в `sched_scheme.ese_hash`),
каждый BI — нет (пересборка Allocation Start раскладку от начала BI не меняет). Снятие строгого режима, простое деление,
расписание хоста — `tdma_own_release`.

### 2.3 uc: доступ к среде по своей таблице (uc/ese_dti.c)

Станция — по `ese_slot_tbl` (как прежде), точка в строгом режиме — по `ese_own_tbl`.

1. **Окна** (события массива SP, начало DTI): в своём окне открыты очереди получателей окна (точка — `peer_cid`
   записи, станция — все её пиры), остальным — пауза причины 8; вне своих окон — пауза всем. Там же запоминаются конец
   окна (`fwsh_sp_gate.own_end_tsf`, для путей SLS без обхода таблицы) и «окна нет» (`init_hold`).
2. **Проверка доступа** `ese_dti_tx_gate` — в `tx_slot_dispatch` до выбора очереди (на каждом доступе к среде, в т. ч.
   внутренняя очередь — keep-alive, TxSS, — и широковещательная точки, которых паузы очередей не закрывают): начинать
   обмен можно, только если идёт своё окно и TXOP по лимиту MAC с хвостом `ESE_TXOP_TAIL_US` (32 мкс: ожидание слота
   ≤ aSlotTime, путь uc до пуска ≤ aSlotTime, SIFS + TXTIME(BlockAck, Control PHY)) кончается до конца окна —
   10.39.6.2 «A STA that initiates a sequence shall check that the frame exchange sequence, including any control frame
   responses, completes before the end of the SP», 10.39.5 для CBAP. Не помещается — отказ (выход как «нет очереди»), и
   лимит TXOP MAC урезается до остатка − хвост − `ESE_TXOP_RETRY_US` (93 мкс: AIFS + CWmin·aSlotTime AC_BE —
   следующий доступ уложится); остатка нет — пауза всем до следующего окна. На начале окна и DTI лимит — снова LMAC
   0x21 (`txop_limit_cur`). В своём SP после отказа с урезанием следующий доступ — сразу (цикл источника, `src_more`): урезанный
   лимит считан от остатка в момент отказа, доступ позже 93 мкс (отсрочка MAC ~90 мкс) снова не проходил и урезал лимит
   заново — каскад отказов, повтор после потерянного BlockAck через 232 мкс (эмулятор 2026-11-14). В CBAP
   урезанный лимит по-прежнему «стареет» — открытая задача.
3. **SLS-инициатор** (TxSS, `internal_tx_isr`): только если весь обмен (ISS + RSS той же длины + 3·MBIFS +
   SSW-Feedback + SSW-Ack + 2·(BRPIFS + BRP ≤ 100 мкс)) помещается до конца своего окна (`ese_dti_sls_fits`); прежняя
   проверка «до конца BI» считала только свою развёртку — SLS переходил TBTT и сдвигал BTI на 0,9 мс (эмулятор).
4. **Цикл источника в своём SP (10.39.6.2) — без механики TXOP CBAP.** В SP право на среду у источника по
   расписанию; RTS/DMG CTS, отсрочка EDCA и CF-End — механика TXOP CBAP (10.23.2), в SP не нужная, а CF-End пиру в SP —
   усечение SP (10.39.8.1 «The CF-End frame releases any time remaining in the SP at the recipient»; у нас Truncatable =
   0). Роль в окне — `fwsh_sp_gate.init_sp` (своё окно, б7 и Allocation Type 0; ставят события окон и проверка доступа
   на каждом доступе — событие окна L1 не разбирает, пока идёт поток TX):
   * **доступ без RTS** (`txop_initiator_open_txop_flow`: режим 0 — путь очереди управления 0x1a, кадр очереди сразу
     после слота и пробы CCA; стенд: режим 0 работает, MAC-STAND «Режим доступа очереди данных»);
   * **обмен** — кадр → ответ через SIFS → следующий кадр: продолжение MAC (`tx_sta_flow_loop`, `rx_txop_continue`),
     как прежде; конец обмена (`tx_cca_check_and_send` → `ese_dti_sp_src_end`) — **без передачи**: ни запроса итога
     (QoS Null MAC), ни CF-End; ожидания txop_event нет (`fixed_sched_run_tx_slot`). Закрытие из `mtp_get_tx_permission`
     (MTP кадра не дал в фазе поиска скорости) идёт через `tx_send_and_await_rx_frame`: запрос итога (QoS Null, No Ack —
     допустимый кадр источника в SP) остаётся, CF-End — нет; проверка раньше запроса итога удлиняла путь «слот → CCA →
     запрос итога» на 12 тактов (эмулятор) — не принято. План
     TXOP MAC (лимит, проверка доступа держит его внутри окна) кончается сам внутри своего SP: Duration кадров обмена —
     NAV третьих станций, которым в чужом SP передавать нельзя и так;
   * **следующий доступ — сразу**, без отсрочки EDCA (`ese_dti_sp_src_cycle` после `bi_dti_start_tx_slot`, до 8
     доступов за вызов, затем — по отсрочке MAC, чтобы L1 не ждал весь SP): кадр очереди (новый или неподтверждённый —
     MAC держит его с битом Retry) уходит после границы слота на свободной среде; повтор после потери — не раньше
     срока ответа (эмулятор: 66,5 мкс после конца потерянного PPDU) — «may retransmit … PIFS after» (10.39.6.2, PLAN
     №50) соблюдён, обмен не за конец SP (проверка доступа);
   * **начало SP**: на событии начала своего SP (`dti_worker` → `ese_dti_sp_src_start`, фаза DTI) источник начинает
     обмен сам («shall initiate the frame exchange sequence … at the start of the SP»), а не после отсрочки MAC
     (эмулятор: первый кадр через 25–28 мкс от начала SP — слот, проба CCA, путь uc);
   * **назначение слушает источник** (рычаг 4 uc/ese_dti.c; 10.39.6.2 «should be in the receive state for the duration
     of the SP in order to receive transmissions from the source»): без RTS приём нечем навести под первый PPDU (стенд
     2026-10-31: точка, слушающая квази-omni, без RTS теряла 96,7 % первых PPDU станции на MCS 8). Станция — в SP
     точки к ней (запись ESE без б7, Allocation Type 0); точка — в SP станции i к ней: запись своей таблицы «SP точка →
     i» несёт `rx_tail_us` (fw: L + w — до конца следующего SP i → точка), на событии конца своего SP uc наводит приём
     на i. Наведение — `rx_mode_configure(3, i)` с `sta_tab[i].rx_sel` вместо `omni_rx_sel` (`fwsh_sp_gate.rx_peer`,
     `rx_end_tsf`), снятие — в следующем своём окне или по `rx_end_tsf`;
   * **SLS в своём SP** — не раньше `rx_flow_timeout_us` + 100 мкс после конца своего обмена (`src_end_tsf`):
     назначение (наш uc, `rx_flow_main`) до этого ждёт кадров обмена и SSW берёт за кадр данных.
   Прежняя попытка «TXOP CBAP без CF-End» (2026-11-07) ломалась на RTS: назначение после TXOP без CF-End сидит в
   `rx_flow_main` (кадры того же TXOP) и RTS следующего TXOP не разбирает (эмулятор: 13 принятых uc RTS из ~200),
   держатель — `cts_fail` → BF. Без RTS следующий PPDU — кадр данных, его `rx_flow_main` и ждёт.
5. **RTS при ожидающем BF**: vendor на RTS пира с ожидающим BF не отвечает (свой SLS идёт следом). С расписанием SLS
   ждёт своего окна (SP пира — до 32 мс): тогда ответ по 10.3.2.9 (DMG CTS при свободном NAV) — uc/rx.c,
   `rx_get_required_response`, флаг `init_hold` читается только при ожидающем BF.

### 2.4 Станция

Разбор ESE (fw/rx.c, таблица vendor — три записи): с 2026-11-10 сначала окна, где станция может начинать обмен
(общее CBAP, SP «я → точка», CBAP остатка — б7), затем SP «точка → я» (только получатель — окно не нужно: ответы
через SIFS разрешены и без него, вне своих окон uc обмен не начинает, `init_hold` = 1). Прежде — по порядку полей:
общее CBAP, SP «точка → я», SP «я → точка», а CBAP остатка при n = 1 (четвёртое поле) отбрасывался — станция в нём
не начинала обмен вовсе (стенд 2026-11-10, §5.1). Исправлено: записи в массив SP
закладывались с **следующего** BI (`schedule_scheme__sum_two`), а точка объявляет расписание маяком того BI, где оно
действует, — весь первый BI нового расписания станция без событий окон молчала (передача закрыта с начала DTI).
Теперь, если до первой записи ещё ≥ 100 мкс (маяк разобран в BTI/A-BFT), — с этого BI
(`ese_start_walk_from_beacon`).

### 2.5 Частые BF под нагрузкой (разбор 2026-11-07)

В эмуляторе строгий режим под нагрузкой давал SLS каждые ~3 мс (без TDMA — единицы за 3 BI). Наблюдатель записи
`link_stat[].bf_reasons` (uc, причина BF) и `txrx_state2` показал два механизма, оба — не расписания:

1. **Причина б1 (поиск скорости, `tx_sta_flow_loop` → `rate_search_pick_tx_params(…, 1)`).** Данные без соглашения
   BA (Normal Ack): в TXOP из нескольких кадров каждое продолжение после Ack идёт веткой «ответ не тот»: Ack
   распознаёт `rx_match_expected_response` (`rx_ack_rcvd = 1`), но следующий `rx_flow_run` флаг обнуляет на входе
   до `rx_nav_update` — там Ack не узнан (`IMM_ACK` без `BAP_EN`/б18 и `rx_ack_rcvd` = 0) → `mac_prepare_txrx_window`
   ставит б7 → `bf_fdbk_step` вносит 1 в историю неудач BA → после порога — фиксация MCS и запрос BF. Порядок —
   vendor (asm `rx_flow__run` 0x930dd4: `st.as [gp,0x10]` — 0x800568 на входе). **Механизм общий:** без TDMA с
   пачками по 3 кадра (тот же эмулятор, TDMA выкл., без BA) — 17 SLS за BI, 15 из них б1. В строгом режиме кадры
   копятся, пока окно закрыто, — TXOP многокадровые, отсюда частота. С соглашением BA (A-MPDU/BlockAck, как под
   iperf) причины б1 нет. Отчёт приёма Ack (r38) у модели — по именам полей, не снят: доказательство — эмулятор.
2. **Причина б2 (`cts_fail` ≥ порога, `tx_sta_run_txop`).** Серии RTS без DMG CTS — в эмуляторе от конца TXOP без
   CF-End с RTS (п. 4 выше — прежняя попытка); с CF-End и в цикле источника без RTS — единичные.

Связь со стендом: на стенде SLS под нагрузкой бывают 0–16 за 30 с с провалами скорости. Причина каждой BF уже есть в
журнале uc — `handle_bf_triggers`, токен 0x1000d94 (cid, set, triggers): б0 — PER поиска скорости, б1 — неудачи BA
поиска скорости (механизм 1), б2 — cts_fail, SSW пира вне BF-режима, поддержание (l1), б3 — история ответов без поиска, б4 — запрос
хоста, б5 — keep-alive. Если на стенде преобладает б1 при BA — механизм 1 шире модели (BlockAck тоже не узнаётся);
если б1 только на кадрах без BA (управление, TID без соглашения) — он же.

Сценарий эфира теста — с соглашениями BA в обе стороны.

### 2.6 Сроки и бюджеты

* `ese_dti_us_to_window_end` (пути SLS: RSS после ISS, Duration SSW-Feedback, повтор Feedback) — без расписания +3
  инструкции (проверка режима), станция — прежний обход ≤ 3 записей, точка — без обхода (запомненный конец окна).
  test_uc_deadlines: rss_after_iss W = 969 из B = 1320 (запас 351 ≥ 264), как до изменений.
* `ese_dti_tx_gate` стоит до ожидания слота (`mac_select_all_sectors_and_wait`), срок «слот → 0x19» его не включает;
  без расписания — одно чтение и ветвление.
* RTS → DMG CTS (`rx_get_required_response`): путь без ожидающего BF — прежний (codecmp: те же инструкции, другая
  раскладка).
* Цикл источника и наведение — вне сроков SIFS: проверка `init_sp` в `txop_initiator_open_txop_flow` и закрытии — до
  ожидания слота; в `tx_slot_dispatch` — запись до ожидания слота; `rx_mode_configure` — на выходе из потоков (не в
  сроке ответа). Наведение приёма точки — на событии конца своего SP, SP станции начинается через L ≥ 150 мкс (запас
  на `rx_mode_configure` — порядка сотни мкс). Пути со сроком не удлинены: замена RTS — в обёртке запроса MTP
  (`txop_open_release_mgmt`, noipa: `txop_initiator_open_txop_flow` отличается только целью вызова, `mtp_queue_release_mgmt`
  пути продолжения TXOP — без изменений), конец обмена в `tx_send_and_await_rx_frame` — проверка байта после запроса
  итога и хвост в отдельной функции (`tx_sp_end_restore_rx`, noipa): пролог и путь «слот → CCA → запрос итога» — те же
  инструкции (только переименование регистров). Первая версия (вызов `ese_dti_sp_src_end` в начале
  `tx_send_and_await_rx_frame`) добавила два сохраняемых регистра — путь «DMG CTS → данные» в эмуляторе на 26 тактов
  длиннее, RDG пира не успевал (test_air `test_live_rd_declined`); исправлено, «RTS → пуск данных» снова 6869 тактов
  (до изменений 6867). codecmp против HEAD: изменены только функции с правкой и `rx_mode_configure`; прочие — адреса
  таблиц переходов и вызовов (сдвиг раскладки ≡ 0 mod 4), ХРУПКО-функции — без изменений. test_uc_deadlines — те же результаты (те же 8 xfail). uc .text +804 Б (117 604 из 131 072).
* Общая память: `ese_own_tbl` 0x857978..0x8579e8, `fwsh_sp_gate` 0x8579e8..0x857a00 (обнуляет crt0 fw): +0x0a

## 5. Стенд (одна станция)

С одной станцией (`tdma_ctl.sh strict 1`): BI — общее CBAP 2 мс, SP точка → станция и станция → точка по 32,7 мс,
CBAP остатка ~32,7 мс. Проверить:
1. маяк: ESE 4 поля (захват PMC, ref/air_judge правило `schedule`); Allocation Start — следующего BI;
2. судья `sp_access` по захвату PMC обоих узлов: передачи точки — только в общем CBAP, своём SP и CBAP остатка,
   станции — в CBAP и своём SP; ответы — в чужом SP; нет кадров за концом окон;
3. iperf вниз и вверх по отдельности: ~ доля своих окон (вниз ≈ 2 + 32,7 + 32,7 из 100 мс, вверх так же); ping —
   задержка до ~70 мс (ожидание окна);
4. `fwsh_sp_gate` (0x8579e8): refused/capped растут, `txop_cap_us` сбрасывается в начале окон; FWERR 0;
5. BF/BRP под нагрузкой: SLS только в своих окнах, без переходов за TBTT (BTI вовремя, судья `bti_delay`).
6. Повтор у конца окна (H-MTPLIM2, не снято): после потери A-MPDU в TXOP CBAP — повтор только если «A-MPDU +
   BlockAck» помещается в остаток TXOP (длина A-MPDU по остатку), CF-End — только при достаточном остатке; иначе кадр
   ждёт следующего доступа. Судья по PMC: `cbap_end`, `txop_limit`, `dti_unallocated` — 0 (эмулятор:
   test_air_strict_sp_retransmit; на прежней версии со старой моделью — `cbap_end`).
7. Цикл источника (не снято; в эмуляторе — допущения ниже):
   * PMC обоих узлов: в SP — ни RTS/DMG CTS, ни CF-End (QoS Null — только после фазы поиска скорости); первый кадр источника — в первые ~30 мкс SP;
     между обменами источника — зазоры от SIFS до ~70 мкс (без отсрочки EDCA);
   * **H-SPNOEND (главное, не установлено)**: следующий доступ (`0x19000b00` + кадр очереди), пока план TXOP MAC
     прошлого обмена ещё идёт (CF-End не было, txop_event не ждали). Эмулятор (с 2026-11-08, H-MTPLIM2 —
     docs/MAC-STAND.md «План TXOP: повтор и продолжение»): новый доступ `0x19000b00` закрывает прежний план, кадр
     начинает новый (Duration — от лимита); повтор после тайм-аута ответа тем же `0x19000b00` план не закрывает.
     Прежде — кадр продолжал прежний план (Duration — его остаток), за его концом — новый план. Снять: Duration подряд идущих A-MPDU источника в SP (PMC),
     FWERR, `mac_mon_report.txop_end_tmo` (+0x6a) — 0, assert uc 0x92/0xaa нет. Если MAC не выпускает кадр до конца
     прежнего плана — урезать лимит TXOP в своём SP до одного обмена (как `ese_dti_txop_cap`) или ждать txop_event
     с этим лимитом;
   * **H-SPRXSTEER (не установлено)**: наведение приёма точки на станцию на время SP станции —
     `fwsh_sp_gate.rx_steers` растёт по разу на SP, первый A-MPDU станции в её SP принят (BlockAck через SIFS; доля
     первых PPDU без ответа — как с RTS, ~0,1 %, а не 96,7 %); iperf вверх — доля окон станции;
   * повторы: `src_rounds` (+0x15) и `src_ends` (+0x16) растут; iperf вниз/вверх не хуже режима с CF-End
     при той же доле окон.
С двумя станциями — то же + станция B молчит в SP станции A (судья `sp_access` `sp_foreign`).

### 5.1 Стенд 2026-11-10: скорость строгого режима (образ d9ca29c4, iperf3 TCP 8 с)

Строгий режим одной станции: выгрузка 82/100, загрузка 122/123 Мбит/с (обычный ~950); `cbap_end` 0 (H-MTPLIM2
подтверждена), FWERR 0. Разбор записей PMC (`tdmaS1`, `tdmaS2`, 177 BI; данных в записи нет — только ответы и кадры
управления):
* SP точки (32,7 мс): медиана 4 обмена (BlockAck станции), последний кадр — через ~1,5 мс от начала SP; SP станции —
  медиана 1 обмен; остальное время SP — тишина;
* CBAP остатка (~31 мс): станция **ни разу не начинает обмен** (RTS станции — 0, только ответы на RTS точки); в общем
  CBAP (2 мс) — начинает (248 RTS).
Причина — таблица окон станции: три записи vendor, четвёртое поле ESE (CBAP остатка) отбрасывалось (§2.4). TCP-ACK
станции к данным точки (загрузка) и данные выгрузки шли только в её SP и в общем CBAP — раз в BI: окно TCP за BI
(≈ 1,5 МБ / 100 мс ≈ 120 Мбит/с). Точка в CBAP остатка, получив окно TCP, ждёт ACK. Исправлено (fw/rx.c, два прохода
по полям ESE): в таблице станции окна «может начинать» в первую очередь; тест test_air_strict_sta_table_keeps_init_windows.

Остаётся по устройству строгого режима: в SP получатель передаёт только ответы (10.39.6.2), TCP-ACK получателя ждут
его окна. Ускорение по стандарту — короче SP с повтором: Number of Blocks / Allocation Block Period (9.4.2.131,
10.39.6.1) — пары SP «точка → станция» / «станция → точка» по ~2–4 мс несколько раз за BI; потребует таблицы станции
больше трёх записей (окна блоков — отдельные записи) и обхода массива SP по блокам — следующий этап. RD в SP (10.29)
не берём: ответчик RDG отклоняет намеренно (MAC-STAND «Ответчик RD глохнет»).

Судья (ref/air_sched, ref/sp), те же записи: 2652 `sp_foreign` «BlockAck от станции (AID None)» и 87 «QoS Null» —
артефакт: ассоциации в записи нет, AID станции неизвестен; теперь AID выводится по SP пары «AP — STA» Extended Schedule
(`_aids_from_schedule`, тесты test_air_sched). 163 `sp_recovery` «AP-получатель передаёт через ~78 мкс» / «забирает
неусекаемый SP» и 156 `sp_first_src` — тоже артефакт: первый кадр SP — BlockAck получателя на A-MPDU источника,
которого в записи нет (ответ без вызова не шлётся, 10.3.2.11, 10.25.3); теперь `sp_unseen_trigger` — «не проверяемо»
(test_sp::test_first_frame_response_to_unseen_source_frame). Итог по записям: `sp_access` — 0 нарушений, 319/322 не
проверяемо. Реальной передачи точки в SP станции до dot11SPIdleTimeout нет.

Снять на новом образе: те же две записи строгого режима (PMC обоих узлов + air_judge) и iperf3 TCP в обе стороны
8 с; ожидание — станция начинает обмены в CBAP остатка (RTS станции в нём > 0), скорость в обе стороны выше
прежних ~100/120 (верхняя оценка — доля CBAP ~1/3 BI от обычных ~950 плюс SP); `cbap_end`, `sp_access`,
`dti_unallocated` — 0; FWERR 0. И UDP (`iperf3 -u -b 1G`) вниз: заполнение своего SP точкой без обратной связи TCP —
проверка, что SP пустеет из-за TCP, а не из-за MAC (ожидание — обмены точки до конца её SP).

## 6. Дальше: динамическое распределение (10.39.7–10.39.9) — план

Сделано (uc/dynalloc.c, tests/unit/test_tdma_dynalloc.py): Duration и Response Offset Poll по ур. (10-18) (n = 1…8,
совпадают с ref/duration.pp_schedule), Duration SPR (10.39.7.2), Duration Grant GP с Grant Ack и без (ref/dynalloc.gp),
кадры Poll и SPR (ref/fields.parse_frame, check_dai). В эфир ещё не подключено.

Что мешает следующему шагу (найдено 2026-11-07):
* опыт для отчёта приёма Poll/SPR (стенд): vendor-AP с фиксированным расписанием (WMI 0xa03) шлёт Grant, Poll — нет;
  поэтому кадры Poll/SPR — от своей точки: образ точки с `UC_DBG` — на начале DTI один Poll (dynalloc.c, RA —
  станция, Response Offset 20) через FIFO прямой передачи (как CF-End); образ станции с меткой `STAMP_RESP_REP` (30:
  r36…r39, r53) и записью 16 октетов буфера приёма 0x804010 на каждом кадре управления. Ждём: какой бит r37 (рядом с
  RTS б0, mmWaveCTS б1, `MAC_RX_REP2_GRANT`) поднимает Poll и SPR, тип в r39 [7:0] (Control Frame Extension), есть ли
  запрос ответа через SIFS (r40 сел. 0xb `sifs_resp`). То же в обратную сторону — SPR станции точке. Без этого приём
  Poll/SPR в uc — по FC из буфера приёма (дольше: чтение буфера на пути SPR через Response Offset);
* отчёт приёма MAC для Poll и SPR не известен (в uc/mac_regs.h из кадров Control Frame Extension — только
  `MAC_RX_REP2_GRANT`); приёмник может различать по FC в буфере приёма (0x804010) — нужен снимок стенда (метка
  STAMP_RESP_REP на Poll/SPR от vendor-AP с фиксированным расписанием или от нашей точки);
* SPR — через Response Offset от конца Poll (до десятков мкс): пуск по GP-таймеру, как SSW-Feedback A-BFT (bti.c);
  срок — test_uc_deadlines;
* выделенное Grant время у станции — доступ в SP без TXOP CBAP: цикл источника (п. 2.3.4) сделан; окну по Grant
  нужно только своё «окно-SP» вне таблицы (начало = PHY-TXEND Grant + Duration, длина — Allocation Duration): проверка
  доступа (`ese_dti_own_left`) берёт его вместе с таблицей, `init_sp` = 1 — дальше тот же путь. Места в
  `fwsh_sp_gate` нет (0x18 Б заняты) — запись окна Grant в uc DCCM;
* эмулятор: air.py не знает кадров Poll/SPR из FIFO (вставка TA, отчёт приёма) — модель по именам полей до снимка.
