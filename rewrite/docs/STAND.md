# Стенд: подготовка узлов только перезагрузкой

Правило проекта: **перезапуск драйвера, прошивки и смена роли узла — только через перезагрузку устройства.**
Выигрыш в минуту на загрузку не стоит рисков: больше времени уходит на погоню за призрачными ошибками и
артефактами быстрого перезапуска.

Что было при быстром перезапуске (стенд, 2026-11):

- `rmmod wil6210` после работы Wi-Fi висел в состоянии D; набор после этого раз за разом снимал питание — узел .12
  перестал грузиться даже в failsafe (восстановлен загрузкой по сети и sysupgrade, 2026-11-07);
- netifd после `wifi down`/`wifi up` на перенастроенном узле — «PHY is undefined for device»;
- после `insmod` своего модуля интерфейс переименовывался в `phy1-*`;
- фантомные «ping 0/15» после перезапуска радио.

## Схема

Одна реализация для pytest-стенда и для ручных записей — `tools/stand/nodeboot.py` (CLI `tools/stand/node_boot.sh`):

1. **Файлы.** `/lib/firmware/wil6210.fw` и `/lib/modules/$(uname -r)/wil6210.ko` — если заданы: запись во временный
   файл, `mv`, `sync`, сверка md5 до перезагрузки (не сошлось — ошибка, перезагрузки нет).
2. **Роль в uci.** Опции прошлого сценария возвращаются к исходным значениям; затем `wireless.radio0.disabled=0`,
   `wireless.default_radio0.disabled=0`, `mode=ap|sta`, `ssid`, `network` (точка — `lan`, станция — по сценарию:
   `wl60` в ручных записях, `[dut] sta_network` в pytest, у станции peer в тесте AP — удалить); затем команды uci
   сценария (опции hostapd, напр. `multicast_to_unicast`) → `uci commit wireless` (и других затронутых конфигов).
3. **Параметры модуля с самого старта** (`no_fw_recovery=Y` у станции на проверяемом образе) — строка
   `options wil6210 … # sparraw-stand` в `/etc/modules.conf` (kmodloader применяет её при загрузке модуля, порядок
   файлов `/etc/modules.d` не важен). Без параметров строка удаляется. Во время работы параметр можно менять через
   `/sys/module/wil6210/parameters/` — это не перезапуск.
4. `sync; sleep 1; sync` → `reboot` → ожидание ssh с **новым** `boot_id`.
5. **Проверки:** строка версии fw в dmesg (`wmi_evt_ready: FW ver. 6.4.1.0-SparRAW(…)` или vendor), md5 fw и модуля =
   записанным, md5 платы `/lib/firmware/wil6210.brd` = `brd_md5` из `stand.toml` (можно префикс), интерфейс в нужной
   роли (`iw dev`: `type AP` / `type managed`), у станции — связь с точкой (`iw dev … link`: Connected), счётчик
   «Firmware error».

Запрещено в наборе и инструментах: `rmmod`, `insmod`, `modprobe`, `wifi down`/`wifi up`/`wifi` для смены роли или
прошивки. Команды сценария (`--uci`, `SPARRAW_AP_UCI`) — только `uci set/delete/add_list/del_list`; `commit` делает
подготовка.

Служебные файлы на узле:

| файл | что |
|---|---|
| `/etc/sparraw-stand.uci` | «ключ=исходное значение» (или «ключ», если его не было) для каждой опции `uci set` сценария: следующая подготовка возвращает их — опция сценария не переживает его |
| `/etc/sparraw-stand.sig` | подпись подготовленного состояния (роль, SSID, сеть, команды сценария, параметры модуля, md5 fw и модуля): если узел уже в нужном состоянии (подпись, md5, FW загружена, интерфейс роли) — перезагрузка не нужна (так peer-точка не перезагружается перед каждой загрузкой dut-станции) |
| строка `# sparraw-stand` в `/etc/modules.conf` | параметры wil6210 с самого старта |

Роль закоммичена: узел, перезагрузившийся сам (паника, сторож) или после снятия питания, поднимается в той же роли с
той же прошивкой. Модуль `wil6210.ko`, записанный однажды, остаётся на узле и без `--ko` (test_boot печатает версию
probe драйвера).

## Адреса и iperf3 — командами после загрузки, не в uci

Адреса 10.60.0.x, sysctl ARP, правила nft, привязка прерываний и `iperf3 -s -D` выставляются после каждой загрузки
обычными командами (`ip addr add`, `iperf3 -D`) — это не перезапуск драйвера. В uci network их **не** коммитим:

- адрес точки — второй адрес на `br-lan`, через который идёт управление узлом по ssh; ошибка в закоммиченной
  `network.lan` отрезает узел от стенда, а восстановление — только руками (failsafe);
- набор не знает и не должен менять сетевую конфигурацию узлов (`wl60` на .12 настроена вне стенда);
- `iperf3 -s`, nft и прерывания всё равно не описываются uci — шаг после загрузки нужен в любом случае, адрес в нём
  ничего не стоит и всегда идемпотентен (`grep -q … || ip addr add`).

## Питание

Снятие питания (Tapo) — **только если узел не отвечает по ssh**:

- после `reboot`: нет ssh с новым `boot_id` за 300 с → одно снятие питания → ещё 300 с → `StandError` с текстом
  «проверить вручную». Узел отвечает со старым `boot_id` дольше 120 с (reboot завис на процессе в D) — один
  `sync; reboot -f` (это всё ещё перезагрузка, не питание); не помогло — `StandError`, питание не снимается, раз
  узел отвечает;
- зависла команда, а узел отвечает по ssh — `StandError` без перезагрузки и без снятия питания (следующая
  загрузка роли перезагрузит узел штатно);
- ssh не отвечает посреди теста — ожидание 240 с (узел мог перезагрузиться сам), затем одно снятие питания;
- за прогон pytest — не больше `[test] max_power_cycles` (по умолчанию 1) снятий питания на узел; дальше —
  `StandError`, без повторов (износ флеша). Ручные инструменты снимают питание только с `TAPO_AP`/`TAPO_STA`
  (`--tapo`), тоже один раз.

Пропажа узла в тестах `test_sta_vanish.py`, `test_ap_vanish.py` (стимул: партнёр исчезает из эфира без
разъединения) — тоже без питания: `sync; reboot -f` по ssh (`Node.vanish`). busybox `reboot -f` (`init/halt.c`)
делает sync и сразу системный вызов reboot, минуя procd: скрипты остановки не выполняются, hostapd/wpa_supplicant и
netifd не останавливаются — Deauth/Disassociation не уходят. В ядре `device_shutdown()` вызывает только `.shutdown`
драйверов, у wil6210 его нет (`pcie_bus.c`), fw ничего не шлёт. (Если это когда-нибудь окажется не так —
мгновенная перезагрузка ядром `echo b > /proc/sysrq-trigger` после sync.) Узел пропадает на время загрузки
(~1–1,5 мин, дольше прежних 15/30 с без питания) и поднимается сам в закоммиченной роли; тест ждёт новый `boot_id`,
FW и интерфейс.

Исключение — `test_ap.py::test_ap_stop`: `wifi down` — проверка останова точки (PCP_STOP); радио обратно не
поднимается, следующая загрузка роли перезагружает узел.

## Как пользоваться

pytest-стенд (`tests/README.md`) — всё само: фикстуры ролей вызывают `Stand.boot_sta()`/`boot_ap()`. Перезапуск
точки в `test_reconnect_after_peer_restart` — `Stand.restart_peer()` (перезагрузка peer).

Узел вручную:

```sh
tools/stand/node_boot.sh 192.168.1.11 --role ap  --fw build/wil6210.fw [--ssid WL60TEST] [--uci "uci set wireless.default_radio0.multicast_to_unicast=0"]
tools/stand/node_boot.sh 192.168.1.12 --role sta --fw build/wil6210.fw --network wl60 [--ko wil6210.ko] [--modparam no_fw_recovery=Y]
tools/stand/node_boot.sh 192.168.1.12 --role sta --no-reboot          # только проверки уже загруженного узла
```

Ключи: `--brd-md5` (или `BRD_MD5`), `--no-link` (станция: не ждать связь), `--link-timeout`, `--tapo <адрес>`
(снять питание один раз, если узел не поднялся; путь к `tapo_plug.py` — `--tapo-tool` или `TAPO_TOOL`). Код выхода:
0 — всё сошлось, 2 — узел загружен, но проверка не прошла (строка `[node_boot] …` перечисляет что), 3 — ошибка
(не поднялся, не те файлы).

Записи (`tools/stand/`, общие переменные — `stand_lib.sh`: `AP`, `STA`, `SSID`, `STA_NET`, `BRD_MD5`, `OUT`):

| скрипт | что |
|---|---|
| `rdrun.sh <fw> <tag>` | оба узла перезагрузкой параллельно, счётчики uc до/после, захват PMC 30 с на обоих + iperf вверх/вниз; `ANALYZE="<команда>"` — разбор двух pcap |
| `bcrun.sh <fw> <tag>` | точка с `multicast_to_unicast=0`, захват 40 с с записями данных, широковещательный и адресный ping, TA CTS-to-self точки |
| `assocrun.sh <fw> <tag>` | точка перезагрузкой, захват точки `CAP_S` с (200), затем станция перезагрузкой в роль STA: в записи её вход (A-BFT/SLS, Probe/Association, первые кадры) |

## Первый прогон после перехода — что смотреть

- `[node_boot]`/`[стенд]` строки: «загрузился (N с)» — реальное время загрузки wAP 60G (таймауты: 300 с до ssh,
  120 с до wmi_evt_ready, 60 с до интерфейса, 120 с до связи станции);
- `uci show wireless.default_radio0` на обоих узлах после загрузки — роль, SSID, сеть; `/etc/sparraw-stand.*`;
  `grep sparraw-stand /etc/modules.conf` и `cat /sys/module/wil6210/parameters/no_fw_recovery` у станции peer в
  тесте AP (должно быть Y);
- станция dut после перезагрузки точки и после своей перезагрузки: нет «link up: no beacon from peer» (раньше
  vendor-точка теряла маяки, когда станция пропадала по питанию без разъединения; reboot должен разъединять
  штатно — проверить; зависшая запись станции всё равно снимается `iw … station del`);
- имя интерфейса после загрузки со своим модулем — `phy0-*`, не `phy1-*`;
- `/lib/modules/$(uname -r)/wil6210.ko` — модуль из `--ko`; без `--ko` на узле остаётся последний записанный;
- сводка pytest «перезагрузка по питанию (узел не отвечал)» — должна быть пустой.
