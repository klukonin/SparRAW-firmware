# Время исполнения инструкций uc (ARC600, 165 МГц)

Цена каждой инструкции и каждого обращения uc в тактах, измеренная на железе (wAP 60G, Sparrow). Таблица — эталон
модели стоимости эмулятора: `tests/unit/costmodel.py` воспроизводит её, `tests/unit/test_cost_model.py` падает при
расхождении больше 0,3 такта. Сроки в uc (SIFS, ответ на кадр, окна BF) считаются в этих тактах, а не числом
инструкций.

## Как измерено

`uc/bench.c` (только в отладочной сборке `UC_DBG="-DUC_BENCH -DUC_STAMP_MASK=0x20000"`). Все тесты в память кода uc не
помещаются — наборы 1–3 (наборы 5 и 6 — не цена операций: единица срока GP-таймера 0x23, `bench.py --gpt`; маска
состояний 0x27, `--e27`), сборка берёт один (`-DUC_BENCH_SET=1` по умолчанию, `=2`, `=3`); `test_cost_model.py` собирает
все. Тест — цикл lp из 16 одинаковых групп операций и замыкающего nop, n = 2 и n = 6 проходов между двумя чтениями
COUNT1 при запрещённых L1. Цена группы = (ΔT − ΔT_nop) / 64 + 1, где ΔT = T(6) − T(2): постоянная часть (вызов, вход в
цикл) вычитается. Тесты идут по одному раз в 20 мс в простое главного цикла и пишутся меткой `STAMP_BENCH`; разбор —
`tools/hwdbg/bench.py`. Медианы по 35–260 замерам на тест, разброс медиан между прогонами ≤ 0,06 такта.

Дробная часть .94 у потоковых тестов — артефакт метода, а не цена: в цепочке из 16 одинаковых групп первая группа
прохода прячет такт ожидания за замыкающим nop предыдущего прохода (64 − 4 = 60 ожиданий на 64 группы). Цена в
установившемся потоке — целое число в столбце «цена».

## Области адресов

| область | адреса | что там |
|---|---|---|
| своя память uc | 0x800000–0x803fff | DCCM: данные uc, стек, журнал uc |
| память fw | 0x840000–0x87ffff | общая с fw: кольца ящика, link_stat, буферы событий |
| блок MAC | 0x886000–0x886fff | регистры MAC (TSF, маски, очереди, маска пробуждения uc) |
| прочие регистры | 0x880000–0x8bffff без блока MAC | RGF (0x880xxx), PHY (0x883xxx) и др. |

## Сводная таблица

«Тест» — имя в `uc/bench.c` / `tools/hwdbg/bench.py`, «группа» — тело одной группы, «стенд» — медиана цены группы,
«цена» — вывод для одной инструкции.

Сама инструкция чтения стоит 1 такт. Ждёт только та инструкция, которой нужен результат (ожидание по регистру
назначения), и обращения к регистрам. Правило перекрытия (модель воспроизводит все тесты таблицы):

- чтения нет — начинается сразу, конец через 12 (MAC) / 9 (прочие);
- идёт одно чтение, которое само никого не перекрывало, и адрес другой — второе выдаётся сразу, конец =
  max(своё начало + задержка − 1, конец первого + 4 для MAC / + 1 для прочих), результат — ещё через 3;
- вне блока MAC (PHY/RGF) так же перекрывается чтение того же адреса, если регистр-приёмник другой: стенд
  2026-10-30, `rx_flow_measure_snr_select_best` — 8 чтений 0x883830 в разные регистры + 37 тактов прочего, 70,9 такта
  на проход (метка `STAMP_SNR_SEL`, MAC-STAND.md); последовательно модель давала 109, по правилу — 77;
- иначе (тот же адрес в тот же регистр — LD_PHY/LD_RGF, тот же адрес блока MAC, или в полёте уже два) — ждёт конца
  всех начатых чтений.

## Особенности, о которых легко забыть

1. **Ожидание по регистру назначения.** Результат загрузки (своя память +2, память fw +4, регистр MAC +12, прочий
   регистр +9) ждёт любая инструкция, которая читает **или пишет** тот же регистр. Две загрузки подряд в один
   регистр стоят как загрузка + ожидание. `pop` — тоже загрузка. Исключение — чтение регистра (MMIO): новое `ld` в
   тот же регистр его результата не ждёт (LD_RGF_LD_MAC).
2. **Флаги для перехода готовы через 3 такта после любой инструкции с .f (cmp, tst, btst, mov.f, and.f …).**
   bcc сразу после неё ждёт 2 такта, выполнен он или нет; две любые инструкции между ними прячут ожидание. Для jcc
   флаги готовы через 2: ожидание 1. Условное исполнение не-переходов (mov.ne) не ждёт.
3. **brcc (сравнение с переходом) вперёд:** с переходом 5, без перехода 1 — против 2 у пары cmp + bcc без ожидания
   флагов (cmp + bcc вплотную — тоже 5). **brcc назад (смещение < 0)** стоит одинаково при любом исходе: 2, если
   прошлое исполнение этого brcc было с переходом, иначе 5. Цикл на brcc: первый проход 5, дальше по 2, выход 2;
   brcc назад, который обычно не выполняется (проверка «повторить, если …»), стоит 5 каждый раз.
4. **Невыровненная цель перехода.** Переход на 32-битную инструкцию по адресу ≡ 2 (mod 4) — +1 такт. Цель —
   16-битная или выровненная — без добавки.
5. **Чтение регистров неблокирующее и перекрывается.** Сама инструкция стоит 1; два чтения разных адресов идут
   почти параллельно (пара MAC — 16 вместо 24, MAC + RGF — 13), третье ждёт обоих. Независимую работу между чтением
   и использованием результата выгодно ставить вплотную после чтения; чтения разных регистров — парами.
6. **Запись в регистр не ждёт завершения** — его ждёт sync (12 тактов от начала записи в MAC, 10 — в прочие).
   Записи подряд идут не чаще раза в 6 (MAC) / 5 тактов. Чтение регистра после записи — не раньше чем через 3.
7. **Память fw — не регистры:** загрузка 3 такта, результат через 4, с шиной регистров не конкурирует.
8. **Константа limm** добавляет 1 такт любой инструкции, включая загрузку по абсолютному адресу и 16-битные
   `add_s`/`mov_s` с limm (6 Б).
9. **Возврат `j_s [blink]` стоит 3**, `j_s.d` — 2 плюс слот. Вызов с возвратом (bl + j_s) — 5 тактов сверх тела.
10. **Дёшево, вопреки ожиданию:** mul64 (1, результат сразу), flag (1), установка lp (1), сдвиг на регистр (1),
    чтение r40 и COUNT1 (1).
11. **brcc без перехода у конца цикла lp:** за 1 инструкцию до LP_END — +4 такта, за 2 — +3, за 3 и дальше — 0
    (BREQ_NT_BACK .25 = 4/16, BREQ_NT и LD_BRNE_NT .19 = 3/16 на проход, BREQ_NT_N3). Направление перехода не
    важно.
12. **Переход по регистру (j, jl, j_s [blink]) берёт регистр на такт раньше прочих:** после `pop_s blink` ждёт 2
    (а не 1), после `mov` в этот регистр — 1. Сразу после `bl` (blink от самого вызова) — без ожидания. Эпилог
    `pop_s blink; j_s [blink]` поэтому стоит на такт больше, чем по таблице загрузок.
13. **Цикл lp с телом из одной инструкции** стоит +1 такт, если проходов два и больше; тело из двух и больше — без
    добавки.

## Проверка на реальном коде

- Отправка события в fw (`uc_send_evt_mac_monitor`, метки `STAMP_EVT`): пять отрезков между метками — модель равна
  стенду на всех пяти.
- Завершение BF (`bf_sm_process_request_fifo`, метки `STAMP_BF_SEG` и временные промежуточные): эмулятор стартует
  со снимка стенда (`UC.from_snapshot`: `blob_uc_data` и `blob_fw_peri` — память fw 0x840000–0x85ffff), снятого за
  ≤ 0,3 с до события; запрос BF ставится в очередь вручную. Путь (записи журнала uc) совпадает со стендом. Три образа
  с разными наборами меток (14, 22 и 26 отрезков): модель 2190 / 2265 / 2360, стенд 2193 / 2275 / 2392 (−0,1…−1,3 %;
  самое большое расхождение — в отрезке, который на стенде сам плавает на 7 тактов). 17 из 22 отрезков — точно или
  ±1, остальные −3…+4. Отрезки на стенде детерминированы (11–12 завершений — одно значение), кроме тех, где uc читает
  TSF (журнал uc, `uc_read_tsf_lo`): разброс 142–163 и 152–159 тактов.
- Последние правила модели (перекрытие чтений, j по регистру, brcc назад, limm у 16-битных) найдены именно так:
  остаток отрезка → метки внутри → шаблон инструкций → микротест → правило.
- Без снимка памяти fw повтор неточен: эмулятор отдаёт на неинициализированную память детерминированный мусор,
  и код идёт другим путём (например, по `link_stat.bf_reasons`).

## Не измерено (взято по аналогии)

- выполненный jcc и `jl` с условием — как j;
- brcc.d, кроме brne.d;
- прочие расширенные регистры ядра — как r40;
- lr/sr других вспомогательных регистров — как COUNT1;
- ld/st с обратной записью адреса (.a/.ab) — как ld/st;
- переход по регистру через 2 и больше инструкций после записи регистра — без ожидания по аналогии;
- три и больше чтений регистров разных адресов подряд (измерены пары и тройка hi, lo, hi);
- вход в прерывание и выход из него (L1/L2).
